# Next.js: SSR, статика и гидратация

Вопросы, которые стоит проговорить вслух. Короткие рецепты App Router лежат в [nextjs-app-router-cheatsheet.md](nextjs-app-router-cheatsheet.md). Общая теория React без Next — в [tricky-react-interview-answers.ru.md](../../react/tricky-react-interview-answers.ru.md) (разделы 32–35).

Сначала механизм рендера: сервер отдаёт не один HTML, `'use client'` не значит «только браузер», гидрируется не всё дерево. Дальше вопросы, которые обычно идут следом: кэш, мутации, middleware, файлы роутера.

## Как проходить

Закрой ответ и скажи его за 60–90 секунд. Если короче 20 секунд, не хватает механизма. Если дольше двух минут, убери пример.

## 0. Что такое гидратация?

Гидратация — это процесс, в котором JavaScript оживляет HTML, уже нарисованный браузером. Сервер заранее прислал готовую разметку. Браузер её показал. Потом приехал код приложения, и фреймворк привязывает к этим существующим узлам состояние и обработчики событий. Узлы заново не создаются.

Без гидратации страница после SSR — это снимок. Заголовок и текст видны сразу, но клик по кнопке ещё ничего не делает: React-обработчика на ней нет. Гидратация этот обработчик вешает.

По шагам, без Next:

1. Сервер выполняет компоненты и отдаёт HTML: `<button>Like</button>`.
2. Браузер парсит HTML и рисует кнопку. Пользователь её уже видит.
3. Скачивается JavaScript.
4. Фреймворк запускает те же компоненты в памяти и получает описание того же дерева.
5. Он сверяет это описание с узлами, которые уже стоят в DOM. Если они совпали, он не создаёт новую кнопку, а запоминает существующую.
6. На эту кнопку вешаются `onClick`, state и всё остальное, что живёт только в браузере.

Пока шаг 6 не случился, кнопка выглядит готовой, но для приложения она ещё неживая. Это и есть разрыв между первым кадром и интерактивом.

Гидратация нужна только там, где HTML уже пришёл с сервера (SSR или статика). В чистом CSR сервер присылает пустую оболочку, JavaScript сам создаёт DOM через `createRoot`. Привязываться не к чему: узлов ещё не было. `hydrateRoot` работает с готовой разметкой. `createRoot` рисует её с нуля.

Сверка на шаге 5 обязана сойтись. Если в HTML написано `Like`, а первый запуск в браузере рисует `Liked`, фреймворк не понимает, какой узел оживлять. Это hydration mismatch: готовую кнопку выбрасывают и создают другую. Подробно это разобрано ниже.

Скажи так: гидратация не рисует страницу. Страница уже нарисована HTML-ом. Гидратация находит эти узлы и делает их интерактивными, когда приехал JavaScript.

## 1. Что сервер отдаёт на запрос страницы?

Две вещи сразу.

1. **HTML.** Браузер рисует его до того, как приедет JavaScript. Пользователь видит текст, а не пустой экран.
2. **RSC payload** (протокол Flight). Это описание дерева: готовые серверные куски, дырки под клиентские компоненты и props, которые в эти дырки кладут. Payload сериализуемый. Функцию, класс или живой `Date` через него не передать.

Server Component выполняется только на сервере. Его код не попадает в браузерный бандл как реализация компонента. В браузере его не вызывают второй раз и не гидрируют: у него нет state и обработчиков, гидрировать нечего.

**Скажи так: сервер шлёт HTML для первого кадра и payload, по которому клиент понимает, из чего дерево собрано. Интерактив живёт только в клиентских дырках.**

## 2. Что на самом деле значит `'use client'`?

Это граница клиентского бандла, а не запрет сервера.

Модуль с этой директивой и всё, что он импортирует, попадает в JavaScript браузера. Тот же компонент Next всё равно рендерит на сервере в HTML, потом браузер его гидрирует: React проходит по уже существующим узлам и навешивает state и события.

Поэтому `window` внутри render клиентского компонента всё равно падает или расходится. Первый проход идёт на сервере, где `window` нет.

**Импортировать Client Component в Server Component можно. Наоборот нельзя: клиентский модуль не умеет исполнить серверный. Если оболочка клиентская,** а внутренность может остаться серверной, серверный узел передают как `children`. Он посчитается на сервере и придёт уже готовым.

`async`**-компонент бывает только серверным. Клиентский компонент не может быть** `async`**. (здесь езе стоит добавить про лейзи лоадинт)** 

Скажи так: `'use client'` отмечает, где начинается интерактив и чей код едет в бандл. Предварительный HTML у такого компонента всё равно есть. Серверный компонент в клиентский файл не импортируют, его передают детьми.

## 3. Чем CSR, SSR, SSG и ISR отличаются, и где тут гидратация?


| Режим       | Когда появляется HTML                                       | Дальше                                        |
| ----------- | ----------------------------------------------------------- | --------------------------------------------- |
| CSR         | Почти пустая оболочка. UI после бандла                      | Браузер создаёт DOM сам                       |
| SSR         | На каждый запрос                                            | Браузер рисует готовый HTML, затем гидратация |
| SSG, static | На сборке, один HTML для всех                               | Та же гидратация                              |
| ISR         | Как static, но страницу пересобирают по времени или по тегу | Та же гидратация                              |


Гидратация не четвёртый режим. Это клиентский шаг после любого готового HTML. `hydrateRoot` цепляется к существующей разметке и не создаёт узлы заново. `createRoot` серверный HTML выбрасывает и рисует дерево с нуля: пользователь видит замену уже готовой страницы, смысл серверного рендера пропадает.

В App Router страница статическая, если её можно посчитать без данных конкретного запроса. Динамической её делают чтение запроса: `cookies()`, `headers()`, `searchParams`, `connection()`. Тогда HTML считается на каждый запрос. Это и есть SSR в терминах Next.

`fetch` с `next: { revalidate: 60 }` оставляет страницу статически кэшированной и обновляет её по расписанию. Это ISR. `revalidatePath` и `revalidateTag` делают то же по событию, обычно после мутации.

В Next 15 `fetch` по умолчанию уже не кэшируется. В шпаргалке фраза «cached by default» описывает поведение Next 14. На собеседовании назови версию, если спрашивают про дефолт кэша. Механизм от этого не меняется: кэш данных и кэш готовой страницы — разные слои.

Скажи так: CSR рисует в браузере. SSR и статика отдают готовый HTML, потом гидратация навешивает события. Статика собирается заранее, SSR — на запрос, ISR — статика с пересборкой. Гидратация — шаг, а не отдельная архитектура.

## 4. Что именно делает гидратация и что она не трогает?

После того как браузер распарсил HTML, приезжает JavaScript клиентских компонентов. React сверяет свой первый render с уже стоящими узлами и вешает на них обработчики. Текст и вёрстка, которые сервер уже отдал, не пересоздаются.

Гидрируются только Client Components. Server Component в этом проходе не исполняется. Его разметка остаётся той, что пришла в HTML.

Пока гидратация куска не закончилась, клик по нему ещё не доходит до React-обработчика. Selective hydration умеет оживить сначала тот кусок, который пользователь уже тронул, не дожидаясь всей страницы.

Скажи так: гидратация не рисует страницу заново. Она оживляет клиентские узлы поверх готового HTML. Серверные компоненты в браузере повторно не вызываются.

## 5. Как проходит один запрос, по шагам?

1. Роутер находит `page.tsx` и layout'ы сегмента.
2. Сервер выполняет Server Components: `await fetch`, доступ к данным, никакого `window`.
3. Client Components тоже проходят первый render на сервере, чтобы попасть в HTML. Хуки состояния получают начальные значения, эффекты не бегут.
4. HTML и RSC payload уходят в браузер. Если есть `Suspense`, оболочка уходит раньше медленных кусков.
5. Браузер рисует HTML.
6. Грузится клиентский бандл. React гидрирует клиентские компоненты.
7. После гидратации работают клики, эффекты и `window`.

`loading.tsx` сегмента — автоматическая граница `Suspense` вокруг этого сегмента. `error.tsx` обязан быть Client Component: ему нужны state и `reset`.

Скажи так: сервер считает дерево и первый кадр клиентских компонентов, браузер рисует HTML, бандл гидрирует только интерактив. Эффекты стартуют после этого, не во время серверного render.

## 6. Зачем streaming и чем `loading.tsx` отличается от своего `Suspense`?

Обычный SSR молчит, пока не готово всё дерево. Медленный блок в корне держит и шапку.

Streaming шлёт байты по мере готовности. Оболочка уходит сразу, на месте медленного куска стоит fallback, готовый HTML дописывается в уже открытый ответ.

Граница одна и та же: `Suspense`. `loading.tsx` вешает её на весь сегмент роута, и писать её руками вокруг `page` не нужно. Явный `<Suspense>` режет страницу мельче: шапка и быстрый список снаружи, медленная панель внутри.

Вложенные границы едут независимо. Streaming не убирает водопад. Если второй запрос начинается только после результата первого, он всё равно стартует позже. Убирается ожидание соседей, которым чужие данные не нужны.

Скажи так: `loading.tsx` — Suspense на сегмент, свой `<Suspense>` — на кусок страницы. Пользователь видит каркас сразу. Зависимые друг от друга запросы стриминг не распараллеливает.

## 7. Откуда берётся hydration mismatch и чем он плох?

Серверный HTML и первый render на клиенте разошлись. React предупреждает, выбрасывает серверный узел и строит его заново. Первый кадр, ради которого делали SSR, пропадает. Может сбиться фокус. Лишняя работа приходится на момент, когда страницу и так оживляют.

Частые причины:

- `Date.now()`, `Math.random()`, `crypto.randomUUID()` во время render;
- ветка `typeof window !== 'undefined'` уже в первом render: на сервере одно дерево, в браузере другое;
- время в таймзоне сервера и таймзоне браузера;
- невалидная вложенность: `<p><div>`, `<p><p>`. Парсер браузера чинит разметку до гидратации, и React видит уже другие узлы;
- расширение браузера дописало атрибут в HTML.

`'use client'` это не лечит. Первый render такого компонента на сервере тоже выполняется.

`suppressHydrationWarning` глушит предупреждение только для текста одного элемента, например часов. Другую структуру элементов он не прощает. Настоящее исправление — одинаковое дерево с обеих сторон. То, что зависит от браузера, обновляют в эффекте, после mount.

Стабильный `id` для связи `label` и `input` даёт `useId`. `Math.random()` на сервере и в браузере даст разные строки.

Если компоненту вообще не нужен серверный HTML (график, карта, код с `window` в теле render), его подключают без SSR:

```ts
const Chart = dynamic(() => import('./chart'), { ssr: false });
```

До бандла там пусто или fallback. Гидрировать нечего: серверного узла не было.

Скажи так: mismatch — разный HTML и первый клиентский render. Его дают случайные значения, `window`, таймзона и кривая вложенность. React выбрасывает серверный DOM. Лечится одинаковым render. `ssr: false` — когда серверный HTML этому компоненту не нужен совсем.

## 8. Что можно передать из серверного компонента в клиентский?

Только то, что сериализуется в RSC payload: строки, числа, обычные объекты, массивы, даты как строки или числа. Нельзя передать функцию (кроме Server Action, у неё особая ссылка), экземпляр класса, `Map` без подготовки, промис как «живой» объект в старых API.

Секрет в props клиентского компонента становится публичным: он окажется в payload и в бандле. Секреты остаются в Server Component, Route Handler или Server Action.

Server Action можно передать в клиентскую форму как `action`. Это не обычная функция из бандла, а ссылка на серверную функцию. Вызов из браузера делает запрос на сервер.

Скажи так: через границу едет JSON-подобное значение. Интерактив и браузерные API остаются по клиентскую сторону, секреты и доступ к базе — по серверную. Функцию в props не кладут, исключение — Server Action.

## 9. Как это сказать одной минутой?

Next на запрос отдаёт HTML и описание дерева. Server Component считается только на сервере и в бандл не входит. `'use client'` — граница интерактива: предварительный HTML плюс гидратация, не «выключить сервер». Гидратация навешивает события на готовый DOM и не трогает серверные куски. Первый render с обеих сторон обязан совпасть, иначе React перерисовывает узел. `loading.tsx` и `Suspense` отдают оболочку сразу, медленные данные дописываются в поток.

## 10. Какие кэши есть в App Router и чем они отличаются?

Их четыре, и это разные слои. Путаница обычно в том, что слово «кэш» относят сразу ко всем.

| Слой | Живёт | Что запоминает |
| --- | --- | --- |
| Request memoization | Один серверный проход | Повторный `fetch` с тем же URL и теми же опциями в одном дереве не уходит в сеть второй раз |
| Data Cache | Между запросами и деплоями, пока его не сбросят | Результат `fetch` |
| Full Route Cache | Между запросами | Готовые HTML и RSC payload статической страницы |
| Router Cache | В браузере, на время навигации | Уже скачанный payload посещённых страниц |

Request memoization не переживает запрос. Два компонента на одной странице позвали один и тот же `fetch` — сеть одна. Следующий пользователь считается заново, если нет Data Cache.

Data Cache хранит ответ `fetch`. В Next 14 `fetch` в Server Component по умолчанию кэшировался. В Next 15 по умолчанию уже нет: чтобы положить ответ в Data Cache, нужны `cache: 'force-cache'` или `next: { revalidate, tags }`. На собеседовании назови версию.

Full Route Cache есть только у страницы, которую можно посчитать без конкретного запроса. `cookies()`, `headers()`, `searchParams` и `connection()` делают страницу динамической: HTML на каждый запрос, готовый маршрут не хранится. Динамическая страница всё ещё может читать закэшированные `fetch`.

Router Cache не заменяет сервер. Это чтобы переход «назад» не мигал. В Next 15 динамические сегменты в нём по умолчанию не держатся.

`revalidatePath('/products')` сбрасывает кэш конкретного URL. `revalidateTag('products')` сбрасывает все `fetch`, помеченные этим тегом, и страницы, которые их читали. Тег нужен, когда одни и те же данные нарисованы на нескольких URL. Путь нужен, когда вы точно знаете адрес.

Скажи так: один проход дедуплицирует `fetch`, Data Cache помнит ответ между запросами, Full Route Cache помнит готовую статическую страницу, Router Cache помнит её в браузере. `revalidateTag` бьёт по данным, `revalidatePath` — по адресу.

## 11. Когда Server Action, а когда Route Handler?

Оба выполняются на сервере. Отличается вход.

Server Action вызывают из дерева React: `action` у формы или функция, переданная в Client Component. Это мутация внутри приложения. Форма может отправиться и без JavaScript. Action не является публичным HTTP API с произвольным методом и статусом.

Route Handler (`app/api/.../route.ts`) — это обычный HTTP-эндпоинт. Его зовут вебхук, мобильный клиент, curl, чужой бэкенд. Здесь нужны свой статус, заголовки и метод `GET`/`POST`.

Права и валидацию делают внутри action или handler. Проверка в браузере — только подсказка интерфейсу: действие можно вызвать напрямую.

`useActionState` хранит результат прошлого вызова и флаг `pending`. Ручной `useState` вокруг `fetch` то же самое собирает сам и забывает прогрессивную отправку формы.

Скажи так: мутация из React-дерева — Server Action. HTTP для внешнего мира — Route Handler. И там, и там сервер сам проверяет вход и права. После успешной мутации кэш сбрасывают `revalidatePath` или `revalidateTag`.

## 12. Что делает middleware и почему его мало для авторизации?

`middleware.ts` выполняется до рендера страницы. Он видит запрос и может редиректнуть, переписать URL, дописать заголовок или проверить, что cookie вообще есть. Исторически это Edge-рантайм: привычных Node API там нет, тяжёлый запрос в базу сюда не кладут.

Matcher ограничивает, на какие пути он вообще запустится. Дырка в matcher — дырка в проверке.

Middleware — порог на входе в URL: нет сессии, отправь на `/login`. Право читать заказ или менять его проверяют там, где читают и меняют: в Server Component, Server Action или Route Handler. Иначе прямой вызов action или кривой matcher обходят экран логина. Авторизация в middleware не заменяет авторизацию у данных.

Скажи так: middleware тонкий и ранний. Редирект и наличие cookie — да. Решение «этот пользователь имеет право на эти данные» — рядом с данными.

## 13. Чем layout отличается от template, и зачем остальные файлы сегмента?

`layout.tsx` оборачивает дочерние страницы и при переходах между ними не размонтируется. State в layout сохраняется. Общие шапка и сайдбар живут здесь.

`template.tsx` тоже оборачивает, но создаётся заново на каждый переход. State сбрасывается. Его берут, когда нужна анимация входа или чистая форма на каждый заход.

`loading.tsx` — Suspense на весь сегмент. `error.tsx` ловит ошибку рендера этого сегмента и обязан быть Client Component: ему нужны state и `reset`. `global-error.tsx` ловит ошибку корневого layout. `not-found.tsx` показывает ответ `notFound()`.

`generateStaticParams` перечисляет параметры, для которых статическую страницу можно собрать заранее: `[{ id: '1' }, { id: '2' }]`. `generateMetadata` считает `<title>` и Open Graph на сервере, в том числе из params. Это не клиентский `useEffect`, который дописывает title после загрузки.

`'use client'` опускают как можно ниже. Клиентская оболочка не обязана делать серверными всех детей: серверный узел передают в неё через `children`, и он по-прежнему считается на сервере.

Скажи так: layout живёт между страницами, template умирает на каждом переходе. `loading` ждёт, `error` ловит и умеет `reset`, `not-found` — это 404. Параметры для статики и метаданные считают на сервере.

## 14. Где можно держать секрет и почему фильтр в клиенте — не защита?

Переменная без префикса видна только на сервере. `NEXT_PUBLIC_` вшивается в клиентский бандл на сборке и читается в браузере. Секрет с этим префиксом уже не секрет.

Список для экрана собирает Server Component и отдаёт клиенту только то, что можно показать. Клиентский фильтр по уже пришедшему массиву удобен для поиска по названию. Он не защищает данные: всё, что пришло props-ом, есть в payload. Чужие заказы нельзя «скрыть фильтром» в браузере. Их не отдают с сервера.

Мутацию делают Server Action или Route Handler. После неё сбрасывают кэш пути или тега, иначе следующий заход увидит старый список из Full Route Cache или Data Cache.

Скажи так: секрет остаётся в серверном коде и в переменной без `NEXT_PUBLIC_`. На клиент уезжает только то, что пользователь имеет право увидеть. Фильтр в браузере улучшает интерфейс, а не доступ.

## 15. Что ещё могут спросить, если копают глубже?

**Parallel routes и intercepting routes.** Папка `@modal` — именованный слот рядом с `children`. Перехватывающий сегмент `(.)photo/[id]` показывает ту же страницу модалкой, если на неё пришли с соседнего URL, и обычной страницей, если открыли адрес напрямую.

**`next/image` и `next/font`.** Картинка получает размер, lazy loading и современный формат, чтобы не прыгала вёрстка. Шрифт скачивается с вашего домена на сборке, без запроса к чужому CDN в рантайме и без скачка текста.

**Pages Router и App Router.** В Pages данные для сервера описывали `getServerSideProps` и `getStaticProps`, компонент страницы был клиентским. В App Router серверный компонент сам `async` и сам делает `await`. Если проект уже на App Router, достаточно этой разницы.

**Partial Prerendering.** Статический каркас страницы отдаётся сразу, дырки с `cookies()` или другим динамическим чтением доезжают отдельно. Это развитие streaming, не отдельный режим в каждом проекте. Имеет смысл, только если спрашивают свежие версии.

Скажи так: модалка по прямому URL — intercepting route. Картинка и шрифт — чтобы не прыгали layout и сеть. Старый Pages Router таскал данные отдельными функциями, App Router делает это в самом серверном компоненте.
