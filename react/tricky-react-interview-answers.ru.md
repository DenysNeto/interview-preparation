## 1. Жизненный цикл рендера и reconciliation

**Вопрос.** Что происходит с момента `setState` до обновления экрана?

React не меняет DOM в обработчике. `setState` только ставит обновление в очередь. Дальше React заново вызывает компоненты, сравнивает новое описание интерфейса с предыдущим и только потом применяет разницу к DOM.

Важная поправка к короткой схеме: reconciliation не отдельный шаг после render. Сравнение деревьев происходит внутри render-фазы. Практический порядок такой:

1. Обновление попадает в очередь.
2. Render: React вызывает функции компонентов и сравнивает новое дерево со старым.
3. Commit: React применяет уже посчитанные изменения к DOM.
4. Запускаются эффекты.

### Кто ставит обновление в очередь

Новый проход нужен, когда меняется то, от чего зависит UI:

- `setState`;
- `dispatch` из `useReducer`;
- значение Context, которое компонент читает;
- внешний store, на который компонент подписан;
- повторный render родителя, который заново создал этот элемент;
- новые props.

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

Клик не пишет в DOM. Он просит React запланировать render. Несколько обновлений из одного события обычно склеиваются в один проход. Это batching, отдельная тема ниже.

### Что такое render

Render — это вызов функции компонента. JSX превращается в обычные объекты, React elements. Концептуально `<button>{count}</button>` выглядит так:

```js
{
  type: "button",
  props: { children: 0 },
}
```

Это ещё не `HTMLButtonElement`. Настоящий DOM-узел на этой стадии не создаётся и не изменяется. Render только описывает, каким интерфейс должен стать.

Поэтому render обязан быть чистым. При тех же props и state функция должна вернуть тот же результат и не должна ничего менять снаружи. React может вызвать её дважды в Strict Mode, приостановить проход, начать его заново или выбросить результат, если пришло более срочное обновление.

В render нельзя:

- вызывать `fetch`;
- писать в `localStorage`;
- менять `document.title` или DOM;
- подписываться на события;
- мутировать props или state.

Побочное действие, выполненное во время отброшенного render, уже произошло. Сеть, подписки и ручная работа с DOM живут в обработчике события, в `useEffect` или, если кадр нельзя показать неправильным, в `useLayoutEffect`.

### Что сравнивает reconciliation

Reconciliation сравнивает дерево элементов прошлого завершённого render с деревом, которое только что вернули компоненты. Цель — понять, какие host-узлы обновить, создать или удалить.

Правила, которые нужно уметь проговорить:

- Тот же тип в той же позиции: узел переиспользуется, меняются только отличающиеся props. Для компонента это значит: экземпляр и его state сохраняются, функция вызывается с новыми props.
- Другой тип в той же позиции (`div` стал `section`, `Counter` стал `Profile`): старое поддерево размонтируется, новое монтируется. State старого экземпляра уничтожается.
- Смена `key` — это другая идентичность, даже если тип и позиция те же. State сбрасывается.
- Списки сопоставляются по `key` среди соседей. Без устойчивого ключа React пары строит по индексу.

React не сравнивает ваше дерево с `document`. Он сравнивает свои деревья, а затем выполняет короткий список DOM-операций.

### Где живёт state

После выхода из функции локальные переменные исчезают. State хранит React, во внутреннем Fiber-узле. Упрощённо идентичность такая:

```text
тип + позиция в дереве + key
```

Повторный render родителя не сбрасывает state ребёнка, если тип и key ребёнка не изменились. React приходит в ту же позицию, узнаёт тот же экземпляр и отдаёт ему прежний state.

```jsx
function App({ dark }) {
  return (
    <div className={dark ? "dark" : "light"}>
      <Counter />
    </div>
  );
}
```

Смена `dark` заново вызывает `App` и `Counter`, но `count` внутри `Counter` остаётся.

### Commit и эффекты

Когда список изменений готов, начинается commit. React синхронно применяет его к DOM: текст, атрибуты, вставка, удаление, ref. Этот проход не прерывается и не выбрасывается. Пользователь не должен увидеть новый заголовок вместе со старым телом из того же обновления.

Дальше, в обычной картине:

```text
изменения DOM
→ useLayoutEffect
→ браузер рисует кадр
→ useEffect
```

`useLayoutEffect` видит уже новый DOM и успевает поправить раскладку до кадра. `useEffect` обычно работает уже после отрисовки, поэтому туда кладут сеть, таймеры и подписки. При смене зависимостей cleanup предыдущего эффекта выполняется до setup следующего.

### На собеседовании

Render — это вычисление следующего дерева элементов, а не запись в DOM. Внутри этого прохода reconciliation сравнивает новое дерево с предыдущим по типу, позиции и key. Проход чистый: concurrent React может его повторить или выбросить. Commit затем синхронно применяет разницу к DOM. State привязан к идентичности экземпляра, поэтому смена типа или key делает unmount и сбрасывает state, а повторный render родителя state ребёнка сохраняет.

## 2. Virtual DOM и diffing

**Вопрос.** Что такое virtual DOM и как React понимает, что именно поменять в браузере?

Virtual DOM — это дерево plain-объектов, которое вернул прошлый render. Это не скрытая копия `document`. Diffing — проход по этому дереву и по новому дереву, чтобы составить список операций для настоящего DOM.

Допустим, было:

```jsx
<div>
  <h1>Hello</h1>
  <button>0</button>
</div>
```

Стало:

```jsx
<div>
  <h1>Hello</h1>
  <button>1</button>
</div>
```

Типы и структура совпали. React не пересоздаёт `div`. Он меняет текстовый узел кнопки с `0` на `1`.

### Правила diffing

Одинаковый тип на той же позиции. `<div className="old" />` стал `<div className="new" />`. DOM-узел тот же, обновляется атрибут.

Разный тип. `<div><Counter /></div>` стал `<section><Counter /></section>`. Родительский тип изменился, поэтому React выбрасывает поддерево целиком и собирает новое. `Counter` тоже монтируется заново, хотя имя в JSX то же. State счётчика пропадёт.

Текст и атрибуты обновляются на месте. Новый объект элемента в JavaScript не означает новый DOM-узел. Элементы создаются на каждом render. Дорогая часть — это работа функций компонентов и те DOM-операции, которые reconciliation всё-таки назначил.

Списки — особый случай. Без ключей два массива сравниваются по индексу. Вставка в начало сдвигает все пары. С `key` React может переставить существующие узлы, а не пересоздавать их.

### Чего virtual DOM не делает

Он не сравнивает ваше дерево со всей страницей на каждый символ. Он сравнивает прошлый результат React с новым. Узлы, которыми React не владеет, в этот diff не входят.

«Virtual DOM быстрее прямых DOM-операций» — плохая формулировка. Прямая точечная запись в DOM может быть быстрее. Выигрыш React в другом: вы описываете состояние, а список записей вычисляется. Цена render — это JavaScript, который выполнился, плюс получившиеся операции. Если компонент на каждый символ заново сортирует десять тысяч строк, diff тут ни при чём: время ушло ещё до сравнения деревьев.

Внутри React элементы превращаются в Fiber-узлы. Fiber — это и есть рабочая структура: экземпляр, state, эффекты, связь с соседями. На собеседовании достаточно сказать, что virtual DOM — популярное имя дерева элементов, а Fiber — внутреннее представление, на котором хранятся state и очередь работы.

### На собеседовании

Virtual DOM — прошлое дерево React-элементов. Diff идёт по типу и позиции: тот же тип переиспользует DOM-узел, другой тип пересобирает поддерево. Списки сопоставляются по key. React не диффит `document`, и новый объект элемента сам по себе не создаёт новый DOM-узел.

## 3. Идентичность компонента, keys и сброс state

**Вопрос.** Когда React сохраняет state, а когда сбрасывает?

State переживает render, только если React узнаёт тот же экземпляр. Идентичность складывается из типа, позиции и key.

### Позиция важнее, чем кажется

```jsx
function App({ editing }) {
  return editing ? <Input /> : <Input />;
}
```

Это два разных места в дереве. Условие выбирает одну ветку или другую. Переключение `editing` размонтирует первый `Input` и смонтирует второй. Черновик исчезнет, хотя компонент называется так же.

Чтобы state жил, в дереве должен оставаться один и тот же элемент:

```jsx
function App({ editing }) {
  return <Input readOnly={!editing} />;
}
```

Условие переехало в prop. Позиция и тип не изменились, текст в поле останется.

Та же ловушка со сменой типа:

```jsx
{
  isAdmin ? <AdminPanel /> : <UserPanel />;
}
```

Это два разных компонента в одном слоте. У каждого свой state, и при переключении он создаётся заново.

### Key как ручной сброс

```jsx
<Editor key={documentId} />
```

`documentId` изменился — для React это уже другой `Editor`, даже если он стоит на том же месте. Старый экземпляр размонтируется, cleanup эффектов выполнится, новый получит начальный state.

Так сбрасывают форму при смене сущности:

```jsx
function App({ selectedUserId }) {
  return <UserForm key={selectedUserId} userId={selectedUserId} />;
}
```

Эффект, который смотрит на `userId` и вызывает `setDraft("")`, делает то же самое хуже: лишний render и гонка с вводом пользователя.

### Key в списке

```jsx
users.map((user) => <UserRow key={user.id} user={user} />);
```

Key говорит: эта строка — этот пользователь, даже если он переехал на другую позицию. React может переставить компонент и забрать с собой его state, фокус и DOM-узел.

Индекс подходит только списку, который не переставляют, не фильтруют и не вставляют в середину. Удалили первую строку — все индексы сдвинулись, и state второй строки окажется на данных третьей. Случайный ключ `key={Math.random()}` во время render ещё хуже: идентичность новая на каждом проходе, список размонтируется целиком.

Ключ уникален среди соседей, а не во всём приложении. Он стабилен для одной и той же сущности. Внутрь компонента он не приходит: `props.key` равен `undefined`. Если ребёнку нужен id, передайте его отдельным prop.

### На собеседовании

State хранится на экземпляре, а экземпляр — это тип, позиция и key. Та же тройка сохраняет state. Смена типа или key делает новый mount. В списках key нужен, чтобы state не приклеивался к индексу. Индекс ломается при вставке и удалении, случайный key ломается на каждом render.

<a id="04-render-vs-commit"></a>

## 4. Render phase и commit phase

**Вопрос.** Чем вычисление UI отличается от применения UI?

Render считает, что показать. Commit это показывает.

### Render можно выбросить

В render React вызывает ваши функции и собирает дерево. Concurrent-режим может:

- начать render низкоприоритетного обновления;
- прервать его из-за клика;
- выбросить незаконченное дерево;
- начать заново уже с учётом клика.

Поэтому всё, что сделано в теле компонента, может случиться повторно или не дойти до экрана. `fetch` в теле компонента отправит запрос даже для выброшенного прохода. Подписка в теле компонента подпишется без гарантированного cleanup.

Единственное обновление state прямо во время render, которое React документирует, — подстройка state, когда изменился prop, например id сущности. Безусловный `setState` в теле компонента зацикливает render.

### Commit выполняется один раз

К commit React приходит уже с выбранным деревом. Он применяет DOM-операции синхронно. Этот кусок не ставится на паузу. Сразу после мутаций запускается `useLayoutEffect`: DOM уже новый, браузер кадр ещё не показал. Потом браузер рисует. Потом `useEffect`.

Отсюда практическое правило:

- посчитать значение для JSX — в теле компонента;
- отреагировать на клик — в обработчике;
- измерить DOM до кадра — в `useLayoutEffect`;
- синхронизироваться с сетью, таймером, подпиской — в `useEffect`.

Баг, который есть только в Strict Mode или только когда обновление прерывается, почти всегда оказывается побочным эффектом в render.

### На собеседовании

Render чистый и может быть повторён или выброшен. Commit один раз записывает DOM и не прерывается. Layout-эффекты идут до paint, обычные эффекты — после. Всё, что нельзя безопасно выполнить дважды, не должно жить в теле компонента.

## 5. Batching и асинхронные обновления

**Вопрос.** Почему после `setState` переменная ещё старая и почему два `setState` дают один render?

Обновление state не меняет текущие переменные. Оно планирует следующий render. `count` в этом вызове функции — снимок того render, в котором обработчик был создан.

```jsx
function onClick() {
  setCount(count + 1);
  console.log(count); // старое значение
}
```

Лог печатает старое число не потому, что React «не успел», а потому что `count` — `const` этого прохода. Новое значение появится, когда React вызовет компонент снова.

### Один render на пачку обновлений

React 18 собирает несколько `setState` в один render. Это работает не только в обработчике клика, но и в `setTimeout`, в `promise.then` и в нативном обработчике. Два вызова в одном `fetch().then` больше не дают два отдельных render, как было в React 17.

```jsx
setCount(count + 1);
setName("Ada");
```

Компонент выполнится один раз, уже с обоими изменениями. `unstable_batchedUpdates` почти не нужен.

`flushSync` выключает эту склейку и заставляет React закоммитить обновление немедленно:

```jsx
flushSync(() => setOpen(true));
tooltipRef.current.measure();
```

Это нужно, только если следующая строка обязана прочитать уже обновлённый DOM. `flushSync` бьёт по производительности, потому что ломает batching и заставляет commit прямо сейчас.

### Object.is и пропуск render

Если следующее значение равно текущему по `Object.is`, React не рендерит потребителей этого обновления повторно. `setCount(0)` при `count === 0` ничего не делает. `setUser({ ...user })` делает: это новый объект, даже если поля те же.

Отдельная ловушка: два раза `setCount(count + 1)` в одном обработчике оба читают один и тот же `count`. Второй вызов не видит результат первого. Очередь функциональных обновлений это чинит, об этом следующий раздел.

### На собеседовании

`setState` планирует render и не меняет локальную переменную. Несколько обновлений из одного события, таймера или промиса склеиваются в один render. `flushSync` форсирует commit, когда следующая строка измеряет DOM. То же значение по `Object.is` render пропускает, новый объект — нет.

<a id="06-functional-updates"></a>

## 6. Функциональные обновления и устаревший state

**Вопрос.** Когда писать `setState(next)`, а когда `setState(prev => ...)`?

Функциональная форма нужна, когда следующее значение считается из предыдущего или замыкание может держать старый снимок.

```jsx
setCount((c) => c + 1);
setCount((c) => c + 1);
```

Каждый updater получает результат предыдущего в очереди, даже если экран ещё не обновился. Итог — плюс два.

```jsx
setCount(count + 1);
setCount(count + 1);
```

Оба выражения прочитали `count` этого render. Второе затирает первое. Итог — плюс один.

Та же ошибка внутри интервала, который один раз замкнул `count`:

```jsx
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, []);
```

`count` навсегда равен начальному. `setCount(c => c + 1)` читает актуальное значение и не требует добавлять `count` в зависимости только ради инкремента.

Если новое значение не зависит от старого, обёртка ничего не даёт: `setUser(data)` достаточно.

### Функция как значение state

React считает функцию, переданную в `setState`, updater-ом и вызывает её. Чтобы положить в state саму функцию, её нужно вернуть из updater:

```jsx
setHandler(() => savedFunction);
```

`setHandler(savedFunction)` вызовет `savedFunction(previousState)`.

Та же развилка у ленивой инициализации. `useState(expensive())` считает значение на каждом render, хотя использует его только на mount. `useState(() => expensive())` считает один раз. Если начальное значение само является функцией, возвращайте её из инициализатора: `useState(() => initialFunction)`.

### На собеседовании

`setCount(count + 1)` дважды в одном обработчике теряет инкремент, потому что оба читают один снимок. Функциональный updater ставится в очередь и видит уже обновлённое значение. Его же используют в эффекте и подписке, где замыкание может быть старым. Чтобы сохранить функцию в state, её возвращают из updater, иначе React её вызовет.

<a id="07-immutability"></a>

## 7. Иммутабельность state

**Вопрос.** Почему нельзя сделать `user.name = "Ada"` и вызвать `setUser(user)`?

React сравнивает прошлый и следующий state через `Object.is`, то есть по ссылке. Мутация меняет поля внутри того же объекта. Ссылка та же, обновление выглядит как «ничего не изменилось», render пропускается. Экран остаётся старым, хотя объект в памяти уже другой. Следующее честное обновление может прочитать уже испорченные данные и тоже решить, что показывать нечего.

```jsx
user.name = "Ada";
setUser(user); // та же ссылка

setUser({ ...user, name: "Ada" }); // новая ссылка
setTodos([...todos, todo]);
setTodos(todos.map((item) => (item.id === id ? { ...item, done: true } : item)));
```

Копировать нужно каждый уровень, который меняется. Новый массив со старыми объектами нормален, если сами объекты не менялись. Объект, у которого изменилось поле, должен быть новым. Иначе список перерисуется, а строка, которая сравнивает props по ссылке, может не увидеть изменение.

Immer и Redux Toolkit позволяют писать «мутирующий» код по draft. На выходе всё равно получается новое дерево. Такой синтаксис законен только внутри draft. Снаружи он по-прежнему ломает обновление.

Иммутабельность нужна не только для сравнения. Concurrent render может быть выброшен. Если во время этого прохода вы мутировали объект, который всё ещё показывает предыдущий экран, мутация уже видна пользователю, хотя commit не случился.

### На собеседовании

React смотрит на ссылку. Мутация плюс `setState` того же объекта render не гарантирует. Новые массивы и объекты создают через spread, `map` и `filter`, без `push` и без правки поля. Вложенное изменение копирует каждый затронутый уровень. Concurrent-режим ещё и требует, чтобы выброшенный render ничего не испортил в текущих данных.

<a id="08-derived-state"></a>

## 8. Производные данные и лишний state

**Вопрос.** Что хранить в state, а что считать во время render?

Если значение целиком вычисляется из props и state, второй слот для него не нужен. Два источника правды разъезжаются.

```jsx
const visible = todos.filter((todo) => {
  if (filter === "open") return !todo.done;
  if (filter === "done") return todo.done;
  return true;
});
const remaining = todos.filter((todo) => !todo.done).length;
```

`visible` и `remaining` существуют только в этом render. Их не надо синхронизировать эффектом. `useMemo` вокруг фильтра — оптимизация ссылки или дорогого расчёта, а не ещё один state.

### Копия prop в state

```jsx
const [value, setValue] = useState(propValue);
```

`value` навсегда останется первым `propValue`. Эффект, который делает `setValue(propValue)` на каждое изменение, добавляет лишний render и затирает то, что пользователь уже отредактировал.

Варианты, в порядке предпочтения:

1. Читать `propValue` напрямую, если свой черновик не нужен.
2. Поставить `key` на поддерево, если при смене сущности весь черновик должен умереть.
3. Подстроить state во время render, если сбрасывается только часть:

```jsx
const [prevId, setPrevId] = useState(id);
if (id !== prevId) {
  setPrevId(id);
  setDraft("");
}
```

React прервёт этот render и начнёт его заново с новым state. Так делают редко. Для сетевых данных этот приём не подходит: загрузка — не подстройка локального черновика.

### На собеседовании

В state лежит то, что нельзя вычислить. Фильтр, сумма, полный URL считаются в теле компонента. Копия prop в state устаревает. Синхронизировать её эффектом — лишний проход. Сброс при смене сущности делает `key`.

<a id="09-controlled"></a>

## 9. Controlled и uncontrolled компоненты

**Вопрос.** Кто владеет значением input: React или DOM?

Controlled: на каждом render значение приходит из state. DOM показывает то, что решил React.

```jsx
<input value={text} onChange={(event) => setText(event.target.value)} />
```

Каждый символ обновляет state, state запускает render, render записывает `value` обратно в input. Поэтому можно на лету валидировать, блокировать кнопку и форматировать текст.

Uncontrolled: значение живёт в DOM. React читает его, когда оно действительно нужно, обычно через ref в `onSubmit`.

```jsx
const ref = useRef(null);

<input ref={ref} defaultValue="Ada" />
// ref.current.value
```

`defaultValue` и `defaultChecked` применяются только при mount. Дальше смена prop ничего в поле не запишет.

### Граница, на которой React предупреждает

Нельзя превращать один и тот же input из одного режима в другой без размонтирования.

- `value={undefined}` — uncontrolled;
- `value=""` — controlled;
- сначала `undefined`, потом строка с сервера — React предупредит, что компонент стал controlled.

Начальное controlled-значение — `""` или другое конкретное значение, а не «пустой state до загрузки». Файл — всегда uncontrolled: у `<input type="file">` свойство `value` программно не задаётся.

Controlled стоит выбирать, когда UI зависит от значения во время набора. Uncontrolled — когда значение нужно один раз, на submit, и render на каждую клавишу ничего не покупает. В React 19 форма может забрать `FormData` из uncontrolled-полей через `action`, не храня каждое поле в state.

### На собеседовании

Controlled input получает `value` и `onChange`, источник правды — state. Uncontrolled хранит текст в DOM, React читает ref или `FormData`. `defaultValue` задаёт только старт. Переход между режимами на живом узле — ошибка. `undefined` и `""` для React разные вещи.

<a id="10-lifting"></a>

## 10. Подъём state

**Вопрос.** Когда state переносят в родителя?

Когда два соседа должны показывать одни и те же данные. State переезжает в ближайшего общего родителя. Родитель становится единственным владельцем и передаёт вниз значение и способ его менять.

```jsx
function App() {
  const [query, setQuery] = useState("");
  return (
    <>
      <SearchBox query={query} onChange={setQuery} />
      <Results query={query} />
    </>
  );
}
```

`SearchBox` не импортирует `Results` и не лезет в его переменные. Данные идут вниз props, события идут вверх callback. Источник правды один, поэтому строка поиска и список не разъедутся.

Поднимать заранее не нужно. Пока значение нужно одному компоненту, оно живёт в нём. Подъём заставляет родителя рендериться на каждое изменение и прокидывать props через промежуточные уровни. Если прокидывание стало цепочкой из пяти компонентов, которые сами значение не используют, это уже повод для колокации ниже, для композиции через `children` или, реже, для Context.

Дублировать state в обоих соседях и синхронизировать эффектами — худший вариант подъёма: два источника и гонка обновлений.

### На собеседовании

Общий state поднимают в ближайшего общего родителя, когда он реально нужен двоим. Вниз уходит значение, вверх — callback. Пока потребитель один, state остаётся локальным.

<a id="11-colocation"></a>

## 11. Колокация state

**Вопрос.** Куда класть state, если его не нужно делить?

В самый нижний компонент, который его читает и меняет. Флаг открытия модалки не живёт на странице, если страница только рендерит модалку. Черновик поля живёт рядом с полем, а не в глобальном store. Подсказка, которая нужна одной карточке, не становится полем Context.

Колокация и подъём — одно правило с двух сторон. Владелец один. Он стоит так близко к читателям, как позволяет совместное использование. Локальный state не будит остальное дерево. Глобальный state на каждый символ будит всех подписчиков.

Серверные данные — исключение из «положи туда, где впервые понадобилось». Их владелец — кэш по ключу запроса, а не тот компонент, который случайно сделал первый `fetch`. Копия списка пользователей в Redux, в Context и в локальном state — три источника, которые надо вручную инвалидировать.

Признак плохой колокации: чтобы поменять поведение одной кнопки, вы читаете store всего приложения. Признак слишком высокого подъёма: родитель знает про `isTooltipOpen` глубокого ребёнка и рендерится от наведения, хотя больше никто этот флаг не читает.

### На собеседовании

State живёт в нижнем компоненте, которому он нужен. Поднимают его только когда появляется второй читатель. Серверные данные не копируют в ближайший компонент: у них общий кэш по ключу запроса.

<a id="12-use-state"></a>

## 12. Инициализация и обновление `useState`

**Вопрос.** Когда читается начальное значение и что именно делает `setState`?

`useState(initial)` берёт `initial` только в момент mount. На следующих render аргумент игнорируется.

```jsx
function Editor({ initialTitle }) {
  const [title, setTitle] = useState(initialTitle);
}
```

Родитель передал новый `initialTitle` — `title` не изменится. Чтобы форма пересоздалась, нужен `key` или явная подстройка state.

Ленивая форма тоже выполняется на mount:

```jsx
const [data] = useState(() => buildExpensiveIndex(source));
```

`useState(buildExpensiveIndex(source))` вызовет функцию на каждом render, а результат выкинет. В Strict Mode инициализатор могут вызвать дважды, поэтому он обязан быть чистым: никакой подписки и никакой записи в глобальную переменную.

### Как ведёт себя обновление

- `setTitle(next)` планирует render. Переменная `title` в этом замыкании остаётся прежней.
- `setTitle(prev => next)` ставит updater в очередь.
- `Object.is` со старым значением пропускает повторный render потребителей. Новый объект никогда не равен старому.
- Несколько `setState` в одном обработчике, таймере или промисе склеиваются.

Хранить функцию в state легко перепутать с обеими формами:

```jsx
useState(() => initialFn); // ленивый init, в state попадёт initialFn
setFn(someFunction);       // React вызовет someFunction как updater
setFn(() => someFunction); // в state попадёт someFunction
```

`setState` в обработчике не возвращает новое значение и ничего не отдаёт через `await`. Дождаться «окончания setState» нельзя. Можно дождаться следующего render через эффект, но обычно это сигнал, что логику пора перенести в сам обработчик.

### На собеседовании

Начальное значение и ленивый инициализатор живут только на mount. Следующие props сами state не обновляют. `setState` планирует проход, равное по `Object.is` значение проход пропускает, новый объект — нет. Функцию в state кладут через `() => fn`, иначе React использует её как updater.

<a id="13-effect-deps"></a>

## 13. Зависимости `useEffect`

**Вопрос.** Что писать в массиве зависимостей и почему его нельзя «просто очистить»?

Массив — это список реактивных значений, которые эффект замкнул. Туда входит каждый prop, state и функция из компонента, которые эффект читает. ESLint `exhaustive-deps` почти всегда прав.

```jsx
useEffect(() => {
  const id = setInterval(() => onTick(count), 1000);
  return () => clearInterval(id);
}, [count, onTick]);
```

Пустой массив значит: «снимок первого render». Это верно только если эффект правда не читает props и state. Удалить `count`, чтобы интервал не перезапускался, — не оптимизация. Интервал навсегда останется с первым `count`. Это устаревшее замыкание.

Чинить цикл зависимостей тоже не удалением. Варианты:

- перенести функцию внутрь эффекта, если снаружи она не нужна;
- стабилизировать её через `useCallback`, если её же ждёт мемоизированный ребёнок;
- положить последнюю версию в ref, если подписка обязана создаваться один раз;
- перестать синхронизировать через эффект то, что считается во время render.

Объект, созданный в render, новый каждый раз. Эффект с зависимостью `options` будет запускаться на каждый проход, если родитель пишет `options={{ page: 1 }}`. Объект либо создают внутри эффекта, либо мемоизируют, если та же ссылка нужна ребёнку.

### Эффект нельзя делать async

`useEffect` ждёт от функции либо ничего, либо cleanup. `async`-функция всегда возвращает Promise. React примет его за cleanup и при следующем запуске попытается вызвать.

```jsx
useEffect(async () => {
  const data = await fetchUser(id);
  setUser(data);
}, [id]);
```

`return () => controller.abort()` после `await` React тоже не увидит: наружу уже ушёл промис, а cleanup должен вернуться синхронно.

Рабочая форма: синхронный эффект, внутри него `async function load()`, вызов `load()`, синхронный `return` с cleanup. Ошибку `await` ловят в `try/catch`. Error boundary её из эффекта не поймает.

### На собеседовании

В зависимости входят все реактивные значения, которые эффект читает. Пустой массив фиксирует первый снимок. Удаление зависимости не замораживает время, оно оставляет старые props. Сам колбэк эффекта синхронный: async-функция возвращает промис, и React принимает его за cleanup.

<a id="14-effect-cleanup"></a>

## 14. Cleanup и порядок эффектов

**Вопрос.** Когда выполняется cleanup и в каком порядке идут эффекты?

Setup выполняется после того, как компонент попал на экран. Cleanup выполняется перед следующим setup с новыми зависимостями и при unmount.

```jsx
useEffect(() => {
  const controller = new AbortController();

  async function load() {
    try {
      const res = await fetch(`/api/users/${id}`, { signal: controller.signal });
      setUser(await res.json());
    } catch (err) {
      if (err.name === "AbortError") return;
      setError(err);
    }
  }

  load();
  return () => controller.abort();
}, [id]);
```

Пользователь открыл `id = 1`, потом быстро `id = 2`. Cleanup первого эффекта отменяет запрос. Ответ для единицы не сможет записать state поверх двойки, если запрос уважает `AbortSignal`. Флаг `let ignore = false` запрещает только `setState`. Сеть при этом дорабатывает до конца.

### Порядок

- В одном компоненте эффекты запускаются в порядке объявления. Их cleanup идёт в том же порядке.
- `useLayoutEffect` выполняется после записи DOM и до paint. `useEffect` — после paint.
- При mount вложенное дерево коммитится изнутри наружу: эффект ребёнка ставится раньше эффекта родителя.
- При смене зависимостей порядок для конкретного эффекта всегда один: cleanup старого, потом setup нового.
- В development Strict Mode делает setup, cleanup, setup ещё раз. В production mount один.

Поэтому подписка без cleanup всплывает именно в Strict Mode: сокет открылся, «закрылся», открылся снова, а первый остался висеть, если cleanup пустой.

`useLayoutEffect` не для загрузки данных. Он блокирует кадр. Туда кладут измерение и синхронную поправку позиции, чтобы пользователь не увидел вспышку неправильной раскладки. На сервере layout нет, и `useLayoutEffect` при SSR предупреждает.

### На собеседовании

Cleanup идёт перед следующим запуском того же эффекта и при размонтировании. В нём отменяют запрос, снимают слушатель и чистят таймер. Layout-эффекты до кадра, обычные после. Внутри компонента порядок — порядок объявления. Strict Mode в development специально гоняет cleanup, чтобы найти дыру.

<a id="15-unnecessary-effects"></a>

## 15. Лишние эффекты

**Вопрос.** Какой код ошибочно кладут в `useEffect`?

Эффект синхронизирует React с внешней системой: подписка, таймер, не-React-виджет, ручной вызов DOM API. Почти всё остальное — либо производные данные, либо реакция на событие.

Считать во время render:

```jsx
const fullName = `${first} ${last}`;
const visible = items.filter((item) => item.active);
```

Эффект, который записывает это в state, даёт лишний кадр: сначала пустое или старое значение, потом правильное.

Реагировать в том обработчике, который уже знает, что случилось:

```jsx
function addTodo() {
  const next = [...todos, todo];
  setTodos(next);
  onChange(next);
}
```

Эффект «когда `todos` изменились, позови `onChange`» сработает и на любое другое изменение списка, включая то, которое пришло от родителя. Получится петля или лишнее уведомление.

Сбрасывать state ключом, а не эффектом, который смотрит на prop и вызывает `setState`.

Не строить цепочку эффектов: один записывает A, второй смотрит на A и записывает B. Это два render и хрупкий порядок. B считается из A в теле компонента, либо обе записи делаются в одном событии.

Загрузка в эффекте допустима, но ей нужен cleanup. Кэш — TanStack Query, loader роутера, Server Component — убирает из компонента гонку, флаги и ручную отмену. Подписка на внешний store — это `useSyncExternalStore`, а не пара `useState` + `useEffect`: эффект опаздывает на кадр и в concurrent-режиме может порвать картинку.

### На собеседовании

Эффект — это синхронизация с внешним миром, а не место для вычислений и не обработчик клика. Производные данные считаются в render. Родителю сообщают из события, которое изменило state. Сброс делает key. Цепочка эффектов, которые пишут state друг другу, — два лишних прохода.

<a id="16-stale-closures"></a>

## 16. Устаревшие замыкания

**Вопрос.** Почему таймер, эффект или `useCallback` видят старые props?

Функция запоминает переменные того render, который её создал. Пока живёт эта функция, она не видит следующие значения, если её саму не создали заново или она не читает актуальное значение специально.

Интервал с пустым массивом зависимостей навсегда держит первый `count`. Эффект без `query` в зависимостях всегда запрашивает первый поисковый запрос. `useCallback(..., [])`, который читает `count`, — та же ошибка, только спрятанная в «стабильную» функцию.

Порядок починки:

1. Добавить значение в зависимости, чтобы эффект или колбэк пересоздавался.
2. Перенести функцию внутрь эффекта. Тогда она не является зависимостью и замыкает свежие значения.
3. Взять функциональный updater, если нужно только предыдущее state.
4. Держать последнюю функцию в ref, если подписка создаётся один раз, а вызывать надо всё равно свежий колбэк.

```jsx
const onTickRef = useRef(onTick);
onTickRef.current = onTick;

useEffect(() => {
  const id = setInterval(() => onTickRef.current(), 1000);
  return () => clearInterval(id);
}, []);
```

Интервал один. Каждый тик читает `onTickRef.current`, который render только что обновил. Это запасной выход, когда подписка правда должна жить долго. Сначала пробуют перенос функции внутрь эффекта.

`useEffectEvent` в React 19.2 делает то же самое явно: функция, которую вызывают из эффекта, всегда видит последние props и state и не входит в зависимости. Во время render её не вызывают.

Выключить `exhaustive-deps`, чтобы предупреждение исчезло, — не починка. Линтер как раз перечисляет значения, которые эффект замкнул. Правило глушат только с комментарием, обычно рядом с ref, который намеренно хранит последнюю функцию.

### На собеседовании

Колбэк видит props и state того render, в котором создан. Пустые зависимости оставляют первый снимок. Сначала значение добавляют в массив или функцию переносят внутрь эффекта. Ref и `useEffectEvent` — когда подписка одна, а колбэк должен быть последним. Глушить lint — значит оставить баг.

<a id="17-ref-vs-state"></a>

## 17. `useRef` и `useState`

**Вопрос.** Оба переживают render. В чём разница?

Запись в state планирует render. Запись в `ref.current` не планирует ничего. React не узнает, что значение изменилось, и экран не обновится.

State — для того, что пользователь должен увидеть. Ref — для всего, что должно пережить render и не является причиной нового render:

- DOM-узел;
- id таймера;
- `AbortController`;
- предыдущее значение, которое не рисуют;
- последний колбэк внутри долгой подписки.

```jsx
const inputRef = useRef(null);
inputRef.current?.focus();
```

`useRef(null)` возвращает один и тот же объект на каждый render. Меняется поле `current`, не сам контейнер.

Читать и писать `ref.current` во время render, чтобы из этого получился JSX, нельзя. React эту запись не отслеживает, а выброшенный concurrent-render может оставить её от прохода, который на экран не попал. Исключение — ленивое заполнение: записать `current`, только если там ещё `null`, и больше не трогать.

Смена ref не запускает `useEffect`. Если на значение нужно реагировать интерфейсом, это state. Предыдущий prop можно запомнить в ref и сравнить в эффекте, но показать «было / стало» на экране так нельзя: во время render в ref лежит значение, которое React не считал данными для UI. Пару «предыдущее и текущее» тогда хранят в state.

### На собеседовании

Ref переживает render и не вызывает render. Туда кладут DOM, таймер, abort и последний колбэк. Всё, что видно на экране, — state. Запись в ref во время render не способ обновить UI.

<a id="18-memo-vs-callback"></a>

## 18. `useMemo` и `useCallback`

**Вопрос.** Что именно они кэшируют и когда от них есть толк?

`useMemo` запоминает результат вычисления, пока не изменятся зависимости. `useCallback` запоминает идентичность функции. `useCallback(fn, deps)` — это `useMemo(() => fn, deps)`.

Первый render они не ускоряют. На нём вычисление всё равно происходит, плюс React хранит ячейку хука. Выигрыш появляется на следующих проходах: либо пропущено дорогое вычисление, либо сохранилась ссылка.

Ссылка нужна в двух случаях:

- ребёнок обёрнут в `memo`, и новый prop на каждом render ломает сравнение;
- значение стоит в зависимостях другого хука, и новая ссылка зря перезапускает эффект или пересчёт.

```jsx
const visible = useMemo(() => items.filter(Boolean), [items]);
const onSelect = useCallback((id) => setSelected(id), []);
```

`setSelected` и `dispatch` уже стабильны. Оборачивать сеттер в `useCallback` не нужно. Объект `style={{ color }}` новый каждый render. Мемоизировать его стоит только если кто-то сравнивает эту ссылку.

Дешёвая мемоизация дороже самой работы: каждый render выделяет хук и сравнивает зависимости. `memo` вокруг кнопки, которая возвращает один элемент, часто медленнее, чем просто вызвать кнопку. Сначала измеряют.

React Compiler, если он включён, вставляет большую часть таких обёрток сам. Ручные `useMemo` и `useCallback` всё равно нужно уметь объяснить: компилятор не видит ссылки, которые приходят извне уже новыми.

### На собеседовании

`useMemo` кэширует значение, `useCallback` — ссылку на функцию. Оба не ускоряют первый render. Их пишут для мемоизированного ребёнка, для зависимостей хука или для измеренно дорогого расчёта. Стабильный сеттер оборачивать не нужно.

<a id="19-custom-hooks"></a>

## 19. Custom hooks и правила хуков

**Вопрос.** Что выносят в свой хук и почему хуки нельзя вызывать в `if`?

Свой хук — функция с именем `useSomething`, которая вызывает другие хуки. Он делит поведение со state, а не JSX и не данные. `useDocumentTitle`, `useDebouncedValue`, `useMediaQuery`.

Два компонента, вызвавшие `useToggle()`, получают два независимых state. Хук не синхронизирует их между собой. Общее значение — это Context или store. Хороший хук прячет эффекты и ref и возвращает маленький контракт: значение и команду.

### Почему порядок вызовов фиксирован

React хранит state хуков списком на Fiber. Индекс в списке — это порядок вызова в данном render.

```jsx
if (isAdmin) {
  useEffect(subscribe, []);
}
const [name, setName] = useState("");
```

На одном render эффект занял слот 0, `name` — слот 1. На следующем `isAdmin` стал false, эффект не вызвался, и `useState` прочитал слот 0, то есть ячейку эффекта. State смешался.

Поэтому:

1. Хуки вызывают только на верхнем уровне. Не в `if`, не в цикле, не во вложенной функции.
2. Хуки вызывают только из компонента или из другого хука.

Условие ставят внутри хука: `if` внутри `useEffect`, а не вокруг `useEffect`. Ранний `return` до хука — та же ошибка. `react-hooks/rules-of-hooks` ловит это статически.

`use` — исключение. Его можно вызвать условно, потому что он находит promise или Context по переданному значению, а не только по номеру слота. Остальные хуки этого не умеют.

### На собеседовании

Свой хук переиспользует логику со state, но каждый вызов владеет своими данными. Хуки идут в одном порядке на каждый render, потому что React адресует их ячейки по номеру вызова. Условие живёт внутри хука. Условный вызов сдвигает все слоты после него.

<a id="20-react-memo"></a>

## 20. `React.memo` и ловушки мемоизации

**Вопрос.** Когда `memo` пропускает render ребёнка, а когда нет?

`memo(Component)` поверхностно сравнивает props. Если каждый prop равен прошлому по `Object.is`, функция ребёнка не вызывается.

Она всё равно вызовется, если:

- родитель передал `onClick={() => ...}` или `items={items.filter(...)}` — это новые ссылки;
- у ребёнка изменился его собственный state;
- изменился Context, который ребёнок читает: `memo` не перехватывает Context;
- prop `children` — это новый элемент, созданный родителем, что происходит почти всегда.

```jsx
const Row = memo(function Row({ user, onSelect }) {
  return <button onClick={() => onSelect(user.id)}>{user.name}</button>;
});
```

`memo` вокруг `Row` бесполезен, пока `onSelect` новый на каждом render родителя. Стабильный `onSelect` и стабильный `user` дают пропуск. Свой `setState` внутри `Row` всё равно её вызовет: `memo` смотрит на props снаружи, а не на хуки родителя. Родитель при этом уже выполнился. `memo` не ускоряет того, кто рендерит детей. Он может ускорить детей.

Своя функция сравнения легко врёт: забытое поле навсегда оставляет старый UI. Её почти никогда не пишут. Мемоизация дешёвого компонента добавляет сравнение и шум. Имеет смысл измеренно медленный ребёнок, и только после того, как его props перестали быть новыми на каждом проходе.

### На собеседовании

`memo` пропускает вызов, если props поверхностно те же. Новый колбэк, новый массив и новый `children` сравнение проваливают. Свой state и Context его обходят. Сначала стабилизируют props, потом оборачивают дорогой компонент. Родителя `memo` не ускоряет.

<a id="21-context"></a>

## 21. Context и лишние рендеры

**Вопрос.** Для чего Context и почему от него рендерится всё поддерево?

Context передаёт значение вглубь без props через каждый промежуточный компонент. Это канал для темы, локали, текущего пользователя, конфигурации дизайн-системы.

```jsx
const ThemeContext = createContext("light");

function App() {
  return (
    <ThemeContext.Provider value="dark">
      <Page />
    </ThemeContext.Provider>
  );
}
```

Каждый, кто вызвал `useContext`, рендерится заново, когда меняется `value` именно этого провайдера. `memo` на потребителе не помогает: обновление пришло не через props.

Обычная авария — новый объект на каждом render:

```jsx
<ThemeContext.Provider value={{ theme, setTheme }}>
```

Даже если `theme` тот же, объект другой. Все потребители просыпаются. Объект мемоизируют или делят на два Context: один для `theme`, другой для `setTheme`. Второй не меняется, и компоненты, которые только вызывают сеттер, не рендерятся из-за смены темы.

Context плохо несёт частые данные: позицию мыши, каждый символ ввода. Обновление будит всех читателей, даже далёких. Для такого лучше store с селектором или state в маленьком поддереве. Провайдер ставят так низко, как позволяют читатели, а не вокруг всего приложения по привычке.

Context не замена подъёму state между двумя соседями. Два соседа дешевле соединить родителем, чем завести провайдер.

### На собеседовании

Context — это значение для поддерева без прокидывания props. Любая смена `value` рендерит всех потребителей, и `memo` это не останавливает. Новый объект на каждом render выглядит как смена значения. Часто меняющиеся данные делят между двумя Context или выносят в store с подпиской на поле.

<a id="22-use-reducer"></a>

## 22. `useReducer`

**Вопрос.** Когда reducer яснее нескольких `useState`?

Когда много событий по-разному меняют один и тот же кусок state и следующее значение зависит от предыдущего. Reducer — чистая функция `(state, action) => nextState`.

```jsx
function reducer(state, action) {
  switch (action.type) {
    case "add":
      return { ...state, todos: [...state.todos, action.todo] };
    case "toggle":
      return {
        ...state,
        todos: state.todos.map((todo) =>
          todo.id === action.id ? { ...todo, done: !todo.done } : todo,
        ),
      };
    default:
      return state;
  }
}

const [state, dispatch] = useReducer(reducer, { todos: [] });
```

`dispatch` стабилен между render. Его можно передать в мемоизированного ребёнка и поставить в зависимости эффекта, не переживая, что ссылка изменится. Вся логика переходов лежит в одном месте, её можно вызвать в тесте без компонента: `reducer(state, action)`.

`useState` остаётся нормальным выбором для одного-двух независимых полей. Несколько `useState`, которые всегда меняются вместе и легко забыть обновить частично, — сигнал собрать их в reducer или хотя бы в один объект.

Если reducer вернул тот же state по `Object.is`, React пропускает render. Ветка `default: return state` как раз про неизвестное действие. Ленивый init — третий аргумент: `useReducer(reducer, userId, buildInitial)`. `buildInitial(userId)` выполнится на mount.

Reducer, который вызывает `fetch` или `setState`, ломает модель. Побочный эффект живёт в обработчике, который потом делает `dispatch` с результатом.

### На собеседовании

Reducer собирает связанные переходы одного state в чистую функцию. `dispatch` стабилен, поэтому удобен как prop и как зависимость. Независимые поля оставляют в `useState`. Эффекты внутри reducer не делают: он только считает следующее состояние.

<a id="23-portals"></a>

## 23. Порталы и всплытие событий

**Вопрос.** Куда портал переносит узел и куда после этого всплывает клик?

`createPortal(child, domNode)` рисует `child` в DOM-узле вне родителя, обычно в `document.body`. Так модалка, тултип и меню выходят из `overflow: hidden` и чужого stacking context.

```jsx
return createPortal(
  <dialog open>{children}</dialog>,
  document.getElementById("modal-root"),
);
```

В дереве React ребёнок остаётся ребёнком того компонента, который вызвал `createPortal`. Меняется только место в DOM.

Клик внутри портала всплывает по React-родителям, хотя DOM-родитель — `body`. `onClick` на компоненте, который создал портал, увидит клик по модалке. `stopPropagation` внутри портала останавливает этих React-родителей.

Он не останавливает нативный слушатель, повешенный на `document` мимо React. Обработчик «клик снаружи» как раз так и пишут. Если он не игнорирует узел портала, модалка закроется тем же кликом, которым открылась: событие дойдёт до `document`, хотя визуально клик был «внутри».

Портал не делает диалог доступным. Фокус, ловушка фокуса, `aria-modal`, имя диалога и возврат фокуса при закрытии остаются вашей работой. Закрытие по Escape тоже.

### На собеседовании

Портал переносит DOM, но не React-дерево. События всплывают к React-родителю. `stopPropagation` не глушит нативный слушатель на `document`, поэтому «клик снаружи» должен явно игнорировать содержимое портала. Доступность диалога портал не добавляет.

<a id="24-synthetic-events"></a>

## 24. Синтетические события

**Вопрос.** Чем обработчик React отличается от нативного слушателя?

React вешает делегированный слушатель на корень приложения, с React 17 это контейнер корня, а не `document`. В обработчик приходит `SyntheticEvent`: кросс-браузерная обёртка с `preventDefault`, `stopPropagation`, `target` и `currentTarget`.

Раньше объект события переиспользовали, и после обработчика поля обнулялись. Сейчас пула нет. `event.target.value` можно прочитать после `await`.

```jsx
<button onClick={handleClick}>Save</button>   // передали функцию
<button onClick={handleClick()}>Save</button> // вызвали во время render
```

Вторая форма выполняет `handleClick` на каждом render и в `onClick` кладёт её возвращаемое значение.

`stopPropagation` останавливает слушателей React. Нативный слушатель на `document` может выполниться всё равно. Порядок зависит от того, на каком корне кто сидит. Несколько React-корней на странице — это несколько делегированных слушателей. Один `stopPropagation` не покрывает оба мира автоматически.

Делегирование значит, что слушатель не висит на каждой кнопке. Для обычного кода это неважно. Это становится важно, когда кто-то вызывает нативный `stopPropagation` на узле ниже корня: React-обработчик на родителе может не увидеть событие, потому что до делегированного корня оно не доплывёт.

### На собеседовании

React делегирует события на корневой контейнер и даёт `SyntheticEvent`. Объект больше не пулится, его можно читать после `await`. В JSX передают функцию, а не результат вызова. Остановка события в React не равна остановке нативного слушателя вне дерева.

<a id="25-forms"></a>

## 25. Формы и валидация

**Вопрос.** Как устроить форму, чтобы ошибки были рядом с полями, а не только в тосте?

Поля делают controlled, если интерфейс зависит от значения во время ввода: живая валидация, счётчик, блокировка кнопки. Если значение нужно только на submit, поля можно оставить uncontrolled и прочитать `FormData`. В React 19 это естественный путь: `action` формы получает `FormData` без ручного `onSubmit`.

Кнопку отключают, пока запрос идёт, и не стирают введённое при ошибке сервера. Иначе пользователь набирает заново то, что он уже ввёл правильно.

Ошибку связывают с полем:

```jsx
<input
  id="email"
  name="email"
  aria-invalid={Boolean(error)}
  aria-describedby={error ? "email-error" : undefined}
/>
{error && <p id="email-error">{error}</p>}
```

Тост можно добавить, но он не заменяет текст у поля. Скринридер должен получить связь через `aria-describedby`, а не только цвет рамки.

На клиенте проверяют для скорости. На сервере проверяют снова. Клиентская проверка не граница безопасности: запрос можно отправить мимо UI. Общая схема, например Zod, не даёт правилам разъехаться.

Большая форма на controlled-полях рендерится целиком на каждый символ. Библиотека вроде React Hook Form изолирует state полей и снимает эту цену. Это оптимизация, а не другая модель HTML.

### На собеседовании

Controlled — когда UI живёт от значения, `FormData` — когда значение нужно на submit. Ошибка сидит на поле через `aria-invalid` и `aria-describedby`. Клиентская проверка для отзывчивости, серверная — потому что клиент не доверяют. На время запроса кнопку блокируют, введённые значения оставляют.

<a id="26-error-boundaries"></a>

## 26. Error boundary и его границы

**Вопрос.** Какие ошибки ловит error boundary, а какие проходят мимо?

Это классовый компонент с `static getDerivedStateFromError` или `componentDidCatch`. Он ловит ошибки рендера, жизненного цикла и конструкторов в дочернем дереве и рисует запасной UI вместо белого экрана. Хука-аналога `componentDidCatch` до сих пор нет.

Не ловит:

- ошибки в обработчиках событий;
- ошибки в `setTimeout`, промисах и `fetch`;
- ошибки в `useEffect`, пока вы сами не поймали их и не записали в state или не бросили заново во время render;
- ошибку в собственном render границы;
- ошибку соседа: граница ловит потомков, не себя и не того, кто стоит рядом.

Событие и запрос обрабатывают через `try/catch` и error state. Маршрут — через `errorElement` роутера. Упавший `React.lazy` и отклонённый promise в `use` граница как раз поймает: сбой всплывает во время render.

Границей оборачивают виджет или маршрут, не только корень. Иначе одна карточка гасит всё приложение. У границы должен быть путь восстановления: кнопка «попробовать снова», которая сбрасывает её state и заставляет детей смонтироваться заново. Без сброса тот же render упадёт снова.

### На собеседовании

Error boundary ловит падения render в детях и показывает fallback. События, промисы и эффекты мимо него. Их кладут в state сами. `lazy` и `use(promise)` граница видит, потому что отказ случается в render. Границ должно быть несколько, на уровне виджета или маршрута.

<a id="27-lazy-suspense"></a>

## 27. Lazy, Suspense и code splitting

**Вопрос.** Как не отправлять пользователю код экрана, который он ещё не открыл?

`React.lazy(() => import("./Settings"))` выносит компонент в отдельный чанк. Пока чанк грузится, рисует не сам lazy-компонент, а ближайший `<Suspense fallback>`.

```jsx
const Settings = lazy(() => import("./Settings"));

<Suspense fallback={<Spinner />}>
  <Settings />
</Suspense>
```

Fallback обязан быть предком lazy-ребёнка. Сам `Settings` свой fallback не выбирает. Ошибку загрузки чанка ловит error boundary: отклонение промиса импорта всплывает как ошибка render.

Режут по маршрутам, не по каждой кнопке. Мелкие чанки добавляют запросы и не уменьшают заметно общий JavaScript. Общий каркас приложения остаётся в основном бандле.

`Suspense` — это не только код. Та же граница ждёт promise, прочитанный через `use`, и Server Component, который приостановился на данных. Вложенные границы открывают страницу кусками: шапка уже на месте, медленная панель показывает свой fallback. Одна граница на всё приложение прячет всё до самого медленного куска.

`lazy` работает только с default export компонента. Вызов `import()` внутри render без `lazy` создаст новый промис на каждый проход. Кэшированием чанка занимается связка `lazy` и бандлер.

### На собеседовании

`lazy` и динамический `import` отделяют экран в чанк. `Suspense` показывает fallback, пока чанк или данные не готовы. Граница стоит над тем, кто ждёт. Делят маршруты. Упавший импорт идёт в error boundary. Тот же механизм ждёт данные, не только JavaScript.

<a id="28-transition"></a>

## 28. Transitions и `useTransition`

**Вопрос.** Как оставить ввод отзывчивым, если новый список рендерится долго?

Обычный `setState` в событии срочный: React старается закоммитить его быстро, потому что пользователь ждёт реакцию на клавишу или клик. Transition — обновление, которое можно прервать. Пока оно считается, на экране остаётся предыдущий UI.

```jsx
const [isPending, startTransition] = useTransition();

function onChange(next) {
  setInput(next);
  startTransition(() => setQuery(next));
}
```

`setInput` срочный, поле не отстаёт. `setQuery` можно выбросить и начать заново на следующую клавишу, поэтому медленный список не блокирует набор. `isPending` истинен, пока transition не закоммитился. Им приглушают список, а не блокируют поле: блокировка поля убивает смысл разделения.

Это не debounce. Промежуточные значения не отбрасываются таймером. Работа выполняется, но с меньшим приоритетом, и устаревший проход можно прервать. Обернуть в `startTransition` ещё и `setInput` — типичная ошибка: тогда и поле обновляется как несрочное, ввод ощущается поздним.

Обновления state внутри async form action в React 19 уже идут как transitions. Отдельный `startTransition` вокруг них не нужен. Transition не делает сам расчёт дешевле. Он не даёт тяжёлому расчёту занять ввод. Если список всё равно считается секунду и пользователь ждёт именно его, нужно уменьшать работу: виртуализация, более дешёвый рендер строки, серверный поиск.

### На собеседовании

Transition помечает обновление как прерываемое. Срочным оставляют ввод, несрочным — тяжёлый результат. Пока новый результат не готов, виден старый, а `isPending` показывает ожидание. Это не задержка по таймеру и не ускорение расчёта. В transition не оборачивают тот `setState`, который должен чувствоваться мгновенно.

<a id="29-deferred"></a>

## 29. `useDeferredValue`

**Вопрос.** Чем отложенное значение отличается от transition, если `setState` вам не принадлежит?

`useDeferredValue(value)` — тот же приоритет, когда значение пришло prop-ом. Вы не можете обернуть чужой `setState`. Вы получаете `query` и отдаёте тяжёлому ребёнку отстающую копию.

```jsx
const deferredQuery = useDeferredValue(query);
const stale = query !== deferredQuery;

return (
  <>
    <SearchInput value={query} />
    <ResultList query={deferredQuery} stale={stale} />
  </>
);
```

Пока список не догнал новый запрос, `stale` истинен, и список можно приглушить. Таймера здесь нет. React откладывает обновление, пока ему нужно сохранить отзывчивость, потом догоняет последним значением. Debounce выбрасывает промежуточные запросы. Deferred value их не планирует по часам: когда время появляется, рисуется актуальное значение.

Без `memo` на `ResultList` оба значения живут в одном компоненте, и этот компонент всё равно выполняется целиком. Откладывание покупает пропуск только у того ребёнка, который получил именно отложенный prop и умеет не рендериться при прочих равных.

`useDeferredValue` не замена загрузки с сервера. Если на каждое значение уходит сеть, гонку и лишние запросы снимают отменой и кэшем, а не только низким приоритетом render.

### На собеседовании

`useDeferredValue` откладывает чужое значение, чтобы тяжёлый ребёнок ещё показывал прошлое. Сравнение с исходным значением даёт признак устаревания. Это не debounce: таймера нет, догоняется последнее значение. Толк есть, когда отложенный prop получает мемоизированный ребёнок.

<a id="30-concurrent"></a>

## 30. Concurrent rendering

**Вопрос.** Что значит «рендер можно прервать» и какую ошибку это вскрывает?

`createRoot` в React 18 включает concurrent-режим. React может готовить несколько версий UI и закоммитить одну. Начатый render можно поставить на паузу, перезапустить или выбросить. Поэтому тело компонента должно быть чистым: выброшенный проход не имеет права оставить подписку, запрос или мутацию.

Что выбираете вы:

- срочное обновление — обычный `setState` в событии, пользователь ждёт именно его;
- transition — `startTransition` или `useDeferredValue`, проход можно прервать;
- `Suspense` — если render ждёт данные, React не коммитит полуготовое дерево. На экране остаётся прошлый UI или fallback.

Tearing — баг, который этот режим проявляет. Один компонент во время render прочитал версию внешнего store №1, его сосед уже версию №2, потому что store — обычная изменяемая переменная. На экране оказываются куски разных моментов времени. `useSyncExternalStore` даёт React снимок и подписку, которые он может перечитать согласованно.

Concurrent-режим не включают руками на каждое обновление. Он уже есть. Transitions и Suspense — способ сказать, какие обновления имеют право подождать.

### На собеседовании

Concurrent rendering умеет бросить незаконченный render и начать заново. Поэтому render чистый. Срочные обновления коммитятся первыми, transitions можно прервать, Suspense не показывает полуготовое дерево. Чтение изменяемого внешнего store во время render рвёт UI. Подписка на такой store идёт через `useSyncExternalStore`.

<a id="31-strict-mode"></a>

## 31. Strict Mode и двойной запуск

**Вопрос.** Почему в development эффект и render срабатывают дважды?

`<StrictMode>` в development специально повторяет работу, которая в production выполняется один раз. Render может быть вызван дважды. Эффект проходит цикл setup, cleanup, setup. В production повторного цикла нет.

Цель — поймать код, который считает, что mount бывает ровно один раз:

- подписка без cleanup;
- мутация во время render;
- запрос, чей ответ применяют даже после cleanup;
- инициализатор state с побочным эффектом.

Двойной запрос в development не значит, что production запросит дважды и не значит, что «Strict Mode сломан». Если второй ответ портит state, у эффекта нет нормального cleanup или запрос должен жить в кэше, который склеивает одинаковые вызовы.

Ленивый инициализатор `useState` тоже должен быть чистым: его могут вызвать дважды. Обработчики событий Strict Mode повторно не вызывает. Сокет, открытый в теле компонента, утечёт именно здесь: render повторился, а пары cleanup у этой записи нет. Открывать его надо в эффекте и закрывать в cleanup.

Предупреждения Strict Mode про устаревшие API — отдельная функция того же режима. Двойной вызов и предупреждения легко перепутать. Двойной вызов ничего не логирует сам по себе. Его видно по двум запросам или двум подпискам.

### На собеседовании

В development Strict Mode дважды рендерит и гоняет эффект через cleanup, чтобы найти одноразовые побочные эффекты. В production этого цикла нет. Чинятся не «двойные вызовы», а отсутствие cleanup и нечистый render. События повторно не вызываются.

<a id="32-server-client"></a>

## 32. Server Components и Client Components

**Вопрос.** Что выполняется только на сервере, а что попадает в браузерный бандл?

Server Component выполняется на сервере. Он может сделать `await` к базе или файлу и отдать результат рендера. Код такого компонента не уезжает в браузер как реализация компонента. У него нет state, эффектов и браузерных API: на сервере нет сессии пользователя в `window`, и перезапускать этот компонент на клик нельзя.

Client Component — модуль с директивой `"use client"`. В нём есть state, эффекты и обработчики. Его всё равно предварительно рендерят на сервере, потом гидрируют. Директива отмечает границу клиентского бандла. Она не значит «пропустить сервер».

Импортировать Client Component в Server Component можно. Импортировать Server Component в клиентский модуль нельзя: клиентский модуль не умеет исполнить серверный. Если оболочка клиентская, а содержимое может остаться серверным, серверный узел передают как `children`. Он отрендерится на сервере и придёт в клиентский компонент уже готовым.

Props через границу сервер → клиент сериализуются. Нельзя передать функцию, экземпляр класса или «живой» `Date`, не превратив его в строку или число. Секреты в клиентском компоненте становятся публичными: они окажутся в бандле. `async`-компонент — серверный приём. Клиентский компонент не может быть `async`.

### На собеседовании

Server Component считает UI на сервере, не попадает в клиентский бандл и не имеет state. `"use client"` начинает клиентский граф: интерактивность есть, предварительный серверный render тоже есть. Серверный компонент в клиентский импорт не кладут, его передают детьми. Через границу едут только сериализуемые props.

<a id="33-ssr-hydration"></a>

## 33. SSR, CSR, SSG и гидратация

**Вопрос.** Чем отличаются способы отдать первую страницу и что такое hydration?

CSR. Сервер отдаёт почти пустой HTML. Браузер скачивает JavaScript и только потом рисует интерфейс. Проще в устройстве. Первый осмысленный экран ждёт бандл.

SSR. На каждый запрос сервер рендерит HTML. Браузер сразу его рисует, затем гидрирует: React проходит по этой разметке и навешивает обработчики, не создавая DOM заново. Первый кадр быстрее, сервер делает больше работы. Первый клиентский render обязан совпасть с HTML, который пришёл с сервера.

SSG. HTML собран заранее, при деплое, а не на каждый запрос. Подходит страницам, одинаковым для всех. Дальше та же гидратация. Обновление по расписанию или по запросу — возможность хостинга поверх этой схемы, не отдельный режим React.

Гидратация — не четвёртая архитектура. Это клиентский шаг после SSR или SSG. `hydrateRoot` цепляется к существующей разметке. `createRoot` выкинет серверный HTML и нарисует дерево заново, это уже путь CSR, и пользователь увидит замену готовой страницы.

`window` во время render, который выполняется и на сервере, читать нельзя: на сервере его нет. Первый клиентский render всё равно должен выдать то же дерево. Браузерное отличие показывают после mount, из эффекта, либо выносят в Client Component, который на сервере рендерит тот же запасной вид.

### На собеседовании

CSR рисует только в браузере. SSR и SSG отдают готовый HTML, потом hydration навешивает события на эту разметку. SSG собирает HTML заранее, SSR — на запрос. Первый render на клиенте обязан совпасть с серверным. `window` в этом render не читают.

<a id="34-hydration-mismatch"></a>

## 34. Несовпадения при гидратации

**Вопрос.** Откуда берётся hydration mismatch и чем он плох?

Mismatch значит: HTML с сервера и первый render на клиенте разошлись. React предупреждает и может выбросить серверный узел, построив его заново. Теряется смысл SSR, может сбиться фокус, цена — лишняя работа в момент, когда страницу и так оживляют.

Частые причины:

- `Date.now()`, `Math.random()`, `crypto.randomUUID()` во время render;
- ветка `typeof window !== "undefined" ? <Client /> : <Server />` уже на первом render;
- время в локали сервера и в локали браузера;
- невалидная вложенность HTML: `<p><div>`, `<p><p>`. Браузер чинит разметку до гидратации, узлы уже не те, что описал React;
- расширение браузера, которое вставило атрибут в разметку.

`suppressHydrationWarning` разрешает расхождение текста на одном элементе, например у отметки времени. На структуру из разных элементов он не распространяется. Настоящее исправление — рендерить одно и то же с обеих сторон. То, что зависит от браузера, обновляют после mount в эффекте.

`useId` даёт id, совпадающий на сервере и клиенте. Id для связи `label` и `input` не строят через `Math.random()`: на сервере и в браузере получатся разные строки, и гидратация разойдётся.

Невалидный HTML стоит проговорить отдельно. React на сервере отдаёт `<p><div></div></p>`. Браузер, разбирая HTML, закроет `p` раньше `div`. К моменту hydration дерево DOM уже другое. Предупреждение выглядит как «React ошибся», хотя разметку починил парсер.

### На собеседовании

Mismatch — разный первый HTML и первый клиентский render. Его дают случайные значения, `window`, таймзона и невалидная вложенность, которую браузер чинит сам. React может выбросить серверный DOM. Лечится одинаковым render с обеих сторон. `suppressHydrationWarning` только для текста на одном узле. Стабильные id даёт `useId`.

<a id="35-streaming"></a>

## 35. Streaming SSR

**Вопрос.** Как отдать страницу, не дожидаясь самых медленных данных?

Обычный SSR ждёт, пока всё дерево посчитается, и только потом шлёт HTML. Streaming шлёт байты по мере готовности. `renderToPipeableStream` и `renderToReadableStream` сначала отдают оболочку, когда она готова (`onShellReady`), потом дописывают куски, которые ждали данные. Браузер уже показывает шапку, а медленный блок доезжает следом. Часто это делает маленький inline-скрипт, который заполняет дырку на месте fallback.

Единица потока — граница `Suspense`. Без неё медленный `await` высоко в дереве держит всю оболочку. Вложенные границы текут независимо: лента может появиться раньше рекомендаций.

Selective hydration может навесить обработчики сначала на тот кусок, с которым пользователь уже взаимодействует, не дожидаясь гидратации всей страницы.

Streaming не убирает водопад. Если B ждёт результат A, B всё равно стартует позже. Он убирает ожидание соседей, которым результаты друг друга не нужны. Тот же принцип, что у `loading`-границ в фреймворках: что обёрнуто в Suspense, то может приехать отдельно.

`onAllReady` ждут, когда HTML нужен целиком до отправки, например для части поисковых ботов или для ответа, который нельзя дописывать. Для интерактивной страницы обычно достаточно `onShellReady`.

### На собеседовании

Streaming отдаёт готовую оболочку и дописывает Suspense-куски по мере данных. Пользователь видит каркас сразу. Граница Suspense решает, что может приехать отдельно. Водопад зависимых запросов при этом остаётся. Selective hydration оживляет сначала тот кусок, который уже тронули.

<a id="36-data-fetching"></a>

## 36. Загрузка данных, гонки и отмена запроса

**Вопрос.** Как не дать медленному ответу перезаписать более новый?

Гонка выглядит так. Пользователь открыл пользователя `1`, потом сразу `2`. Ответ для `1` пришёл последним и записал себя поверх `2`. На экране первый пользователь, в адресе второй.

В эффекте предыдущий запрос отменяют в cleanup:

```jsx
useEffect(() => {
  const controller = new AbortController();

  async function load() {
    try {
      const res = await fetch(`/api/users/${id}`, { signal: controller.signal });
      if (!res.ok) throw new Error(`Request failed: ${res.status}`);
      setUser(await res.json());
    } catch (err) {
      if (err.name === "AbortError") return;
      setError(err);
    }
  }

  load();
  return () => controller.abort();
}, [id]);
```

Эффект остаётся синхронным. `load` — внутренняя async-функция. Cleanup вызывается и при смене `id`, и при unmount. `AbortError` — не ошибка для пользователя, её не кладут в error state.

Флаг `ignore` слабее. Он не даёт старому ответу вызвать `setState`, но браузер всё равно докачивает тело. `AbortController` просит браузер бросить ответ. В React 18 запись state после unmount больше не считается отдельной аварией. Логическая ошибка — записать устаревшее тело — остаётся.

TanStack Query ключует кэш как `["user", id]`, передаёт `signal` в `queryFn` и игнорирует разрешение, которое уже не относится к активному наблюдателю. Loader роутера стартует загрузку до render этого экрана, поэтому соседние данные не ждут mount друг друга.

Водопад появляется, когда независимые запросы выстроены в цепочку. `await fetchUser()`, и только потом `await fetchPosts()`, хотя посты не зависят от пользователя. Их запускают вместе через `Promise.all` или двумя параллельными запросами. Водопад по глубине дерева другой: родитель смонтировался, ребёнок смонтировался, и только тогда ребёнок начал свой `fetch`. Независимые данные поднимают в loader или в родителя.

Ключ запроса включает всё, от чего зависит URL. `["user"]` на всех id — один слот кэша на разных людей.

### На собеседовании

Медленный ответ предыдущего id не должен побеждать. В эффекте это `AbortController` в cleanup, async-функция объявлена внутри, `AbortError` глотают. Флаг `ignore` только блокирует `setState`. Кэш и loader снимают эту работу с компонента. Независимые запросы начинают вместе, а не после mount каждого ребёнка.

<a id="37-optimistic"></a>

## 37. Оптимистичные обновления

**Вопрос.** Когда интерфейс можно обновить раньше ответа сервера?

Когда успех вероятен, а откат понятен. Переключение todo — хороший случай. Платёж — плохой: ложный успех здесь дороже, чем секунда ожидания.

Картина одна. Сначала показывают ожидаемый результат. Если запрос упал, возвращают прежнее. Когда запрос завершился, источником правды становится ответ сервера, а не догадка клиента.

`useOptimistic` держит временную копию, пока идёт transition или action, и сам от неё отказывается, когда действие закончилось. Снимок правды остаётся в state или в кэше.

В TanStack Query то же делают руками вокруг кэша:

- `onMutate` отменяет текущие refetch, запоминает снимок и записывает ожидаемое значение;
- `onError` возвращает снимок;
- `onSettled` инвалидирует запрос, чтобы победила серверная копия.

Без ветки ошибки экран после 500 продолжает врать. Без финальной инвалидации клиент может навсегда остаться со своей догадкой, даже если сервер поправил поле иначе, например обрезал строку.

Оптимистично обновляют то, что пользователь только что сделал сам. Чужие совместные правки так не угадывают: их источник — сервер, и конфликт надо показать, а не затереть локальной версией.

### На собеседовании

Оптимистичное обновление сразу показывает вероятный результат и обязано уметь откатиться. Todo подходит, платёж нет. В кэше это снимок, запись ожидаемого значения, восстановление на ошибке и инвалидация в конце. `useOptimistic` делает временную копию на время transition и сам возвращается к источнику правды.

<a id="38-external-store"></a>

## 38. Внешние store и `useSyncExternalStore`

**Вопрос.** Как читать данные, которые живут вне React, и не порвать интерфейс?

Внешний store — изменяемые данные с собственной жизнью: `navigator.onLine`, Redux, Zustand, переменная модуля. Если читать их прямо в render, concurrent-проход может увидеть две версии: до обновления и после. Соседние компоненты нарисуют разные моменты. Это tearing.

`useSyncExternalStore` отдаёт React три вещи: подписку, снимок для клиента и снимок для сервера.

```jsx
const online = useSyncExternalStore(
  (onStoreChange) => {
    window.addEventListener("online", onStoreChange);
    window.addEventListener("offline", onStoreChange);
    return () => {
      window.removeEventListener("online", onStoreChange);
      window.removeEventListener("offline", onStoreChange);
    };
  },
  () => navigator.onLine,
  () => true,
);
```

`subscribe` регистрирует колбэк и возвращает отписку. `getSnapshot` возвращает текущее значение. Если данные не менялись, снимок обязан быть той же ссылкой. Новый объект на каждый вызов заставит React рендерить бесконечно: он увидит «изменение», перерендерит, снова попросит снимок и снова получит новый объект. `getServerSnapshot` — то, что рендерит сервер, чтобы гидратация совпала. Для чисто клиентского store его всё равно продумывают: без него серверный HTML и первый клиентский render разойдутся.

Пара `useState` и `useEffect`, которая копирует store в state, опаздывает на кадр и от tearing не защищает. Redux и Zustand внутри подписываются через `useSyncExternalStore`. Свой велосипед для того же браузерного API не нужен, если библиотека уже даёт хук.

### На собеседовании

Внешние изменяемые данные нельзя просто читать в render: concurrent-режим порвёт кадр. `useSyncExternalStore` принимает подписку и снимок. Снимок должен быть стабильной ссылкой, пока данные те же, иначе получится бесконечный render. Серверный снимок нужен, чтобы гидратация совпала. Копия в state через эффект опаздывает.

<a id="39-composition"></a>

## 39. Композиция компонентов

**Вопрос.** Как расширять компонент, не добавляя булев флаг на каждый случай?

Через `children` и именованные слоты. Родитель владеет раскладкой. Вызывающий код владеет содержимым.

```jsx
function Card({ title, children, footer }) {
  return (
    <section>
      <h2>{title}</h2>
      {children}
      <footer>{footer}</footer>
    </section>
  );
}
```

`Card` не знает, лежит внутри форма или список. Ему не нужны `showFooter`, `isForm` и `variant="everything"`.

Специализация — тонкая обёртка, а не ещё одна ветка:

```jsx
function PrimaryButton(props) {
  return <Button variant="primary" {...props} />;
}
```

Containment — это `children`. Specialization — обёртка. Эти два приёма закрывают большую часть просьб «добавь флаг». Когда дети ещё и делят скрытое состояние, получается compound-компонент: табы, меню, поле с подписью.

Компонент с десятком булевых props плох тем, что комбинации никто не проверял. `isPrimary && isDisabled && showIcon` рисует состояние, о котором автор не думал. Композиция оставляет каждую вариацию явным JSX.

### На собеседовании

Вместо набора флагов компонент принимает `children` и слоты. Раскладка остаётся внутри, содержимое снаружи. Частный случай — тонкая обёртка. Общее скрытое состояние нескольких детей — уже compound-компонент, не ещё один prop.

<a id="40-render-props-hoc"></a>

## 40. Render props, HOC и хуки

**Вопрос.** Как раньше делили логику и чем это заменили хуки?

Render prop — prop-функция, которая возвращает UI. Ребёнок владеет поведением и зовёт функцию с данными:

```jsx
<Mouse>{(pos) => <Dot x={pos.x} y={pos.y} />}</Mouse>
```

`children` как функция — тот же приём. Он уместен, когда родитель должен сам решить разметку каждой единицы, а ребёнок владеет автоматом: headless-список, disclosure, drag-and-drop.

HOC — функция, которая принимает компонент и возвращает компонент: `withAuth(Page)`. Она добавляет props или поведение обёрткой. За это платят отдельно: ref надо пробрасывать, имя компонента в DevTools теряется без `displayName`, props внешней и внутренней обёртки могут называться одинаково. Типы быстро становятся шумом.

Хук забирает ту же логику без обёртки в дереве:

```jsx
const pos = useMouse();
return <Dot x={pos.x} y={pos.y} />;
```

Компонент сам решает разметку. Дерево не растёт на каждую способность. Хуки заменили большинство HOC и render props там, где делились данные и поведение. Render prop остаётся, когда вызывающему коду нужна власть над разметкой каждого элемента, а не только над результатом хука.

Несколько HOC друг на друге (`withRouter(withAuth(withTheme(Page)))`) трудно читать и отлаживать. Тот же набор в виде хуков — несколько строк в начале функции.

### На собеседовании

Render prop отдаёт разметку вызывающему коду, HOC оборачивает компонент, хук переиспользует логику без лишнего узла в дереве. Хуки заменили большинство обёрток. Render prop оставляют headless-компонентам, где родитель рисует каждый элемент сам.

<a id="41-compound"></a>

## 41. Compound-компоненты

**Вопрос.** Как сделать набор компонентов, которые работают вместе и не требуют гигантского конфига?

Compound-компонент — семейство компонентов с общим неявным состоянием. Их используют вместе, а раскладку задаёт вызывающий код.

```jsx
<Tabs>
  <Tabs.List>
    <Tabs.Tab id="a">Обзор</Tabs.Tab>
    <Tabs.Tab id="b">История</Tabs.Tab>
  </Tabs.List>
  <Tabs.Panel id="a">...</Tabs.Panel>
  <Tabs.Panel id="b">...</Tabs.Panel>
</Tabs>
```

`Tabs` держит выбранный id в Context. `Tab` и `Panel` его читают. Снаружи не передают массив `tabs={[{ id, label, content }]}`, который родитель потом сам интерпретирует. Порядок, обёртки и дополнительная вёрстка остаются в JSX.

Состояние делят через Context, не через `React.Children.map` и `cloneElement`. Клонирование ломается, как только между родителем и табом появляется чужая обёртка: родитель больше не видит нужный тип среди непосредственных детей. Context доходит сквозь обёртку.

`Tab` вне `Tabs` не имеет провайдера. В таком случае хук должен бросить понятную ошибку, а не молча работать с `undefined`. Так же устроены аккордеон, меню и поле, которому нужен общий id с `label`.

Гибкость — и цена. Вызывающий код может собрать бессмысленную комбинацию. Контракт держат документацией, ошибкой вне провайдера и примером правильной сборки. Для простого списка из трёх вкладок без кастомной раскладки обычный массив и один компонент проще. Compound окупается, когда потребителю нужно вставлять свой JSX между частями.

### На собеседовании

Compound-компоненты делят состояние через Context и собираются как JSX, а не как большой конфиг. `cloneElement` по детям ломается на обёртке, Context — нет. Использование части вне родителя должно падать явной ошибкой. Приём нужен табам, меню и полям, где потребителю важна своя раскладка.

<a id="42-a11y"></a>

## 42. Доступность в React

**Вопрос.** Что в React-приложении ломает доступность, хотя клик мышью работает?

React не делает `div` доступным. Элемент выбирают по поведению, которое у него уже есть в браузере. Кнопка — действие. Ссылка — переход. `label` — подпись к полю. Клик на `div` невидим для клавиатуры и для вспомогательных технологий, пока вы сами не восстановите роль, `tabIndex` и обработчики клавиш. Обычно забывают хотя бы клавишу Space или состояние нажатия.

Ошибку поля связывают с ним самим: `aria-invalid` и `aria-describedby`. Иконка без текста получает доступное имя через `aria-label`. Цвет рамки не заменяет текст ошибки.

Фокус двигают намеренно. После перехода на новый маршрут его ставят в заголовок или на основной контент, иначе пользователь скринридера остаётся в старом месте. Диалог при открытии забирает фокус, запирает его внутри и закрывается по Escape. При закрытии фокус возвращается на кнопку, которая диалог открыла. Портал место в DOM меняет, эту работу он не делает.

Асинхронный результат, который не получает фокус, объявляют живой областью: `aria-live="polite"` на тосте или на фразе «сохранено». Иначе событие видно только глазами.

`useId` связывает `label` и `input`, когда id нужно сгенерировать. `Math.random()` для этого id ломает и доступность при гидратации: подпись смотрит на id с сервера, поле уже с другим. Нехватающую семантику добирают ARIA. Если есть нативный элемент, ARIA ему не замена.

### На собеседовании

Берут нативный элемент: `button`, `a`, `label`. Ошибку связывают с полем, у иконки есть имя. Диалог ловит фокус, держит его внутри и возвращает назад. Тост без фокуса объявляют через `aria-live`. Id для связи генерирует `useId`, не `Math.random()`.

<a id="43-testing"></a>

## 43. Тестирование компонентов, хуков и async

**Вопрос.** Что проверяет тест компонента, если он не лезет в state?

Поведение, которое доступно пользователю. React Testing Library рендерит компонент, а элементы ищут по роли, подписи или тексту. `useState` в тесте не читают. Рефакторинг хука не должен ломать тест экрана, если экран ведёт себя так же.

```jsx
render(<TodoApp />);
await userEvent.type(screen.getByLabelText("New task"), "Ship it");
await userEvent.click(screen.getByRole("button", { name: "Add" }));
expect(screen.getByText("Ship it")).toBeInTheDocument();
```

`getBy` бросает, если узла нет. Им пользуются, когда элемент уже должен быть на экране. `queryBy` возвращает `null`, поэтому им проверяют отсутствие. `findBy` возвращает промис и ждёт появления. Им пользуются после запроса и любого обновления, которое ещё не нарисовано.

`userEvent` проходит ту же цепочку, что браузер: фокус, нажатие клавиши, ввод. `fireEvent` прыгает сразу к событию и пропускает то, что завязано на фокус. Для форм берут `userEvent`.

Сеть мокают на границе HTTP, например через MSW, а не подменой `fetch` внутри модуля компонента. Тогда тест проходит настоящие состояния загрузки и ошибки. `renderHook(() => useCounter())` проверяет хук без искусственного компонента. Хук оборачивают в те же провайдеры, которые нужны ему в приложении.

Предупреждение `act(...)` значит: обновление произошло вне ожидания теста. Обычно хватает `await screen.findBy...`, а не ручного `act` вокруг каждого клика. RTL уже оборачивает синхронные действия. Таймеры и `userEvent` вместе требуют явной политики фейковых таймеров, иначе набор текста и debounce ждут по-разному.

### На собеседовании

Тест ищет то, что видит пользователь: роль, подпись, текст. `getBy` требует узел, `queryBy` проверяет отсутствие, `findBy` ждёт асинхронный результат. Ввод идёт через `userEvent`. Сеть мокают снаружи компонента. State и приватные функции не утверждают: тест должен пережить рефакторинг.

<a id="44-profiling"></a>

## 44. Профилирование и преждевременная оптимизация

**Вопрос.** Как понять, какой render правда дорогой?

Записывают конкретное действие в React DevTools Profiler. Смотрят фактическое время и причину: изменились props, state, хук или отрендерился родитель. Чинют горячего родителя, который заставляет работать большое поддерево. Компонент на 0,1 мс в `memo` не нуждается.

Порядок работы:

1. Опустить часто меняющийся state ниже, чтобы он не стоял над большим деревом.
2. Разделить Context, чтобы частые значения не будили медленных потребителей.
3. Обернуть в `memo` дорогой компонент и стабилизировать props, которые он сравнивает.
4. Поставить `useMemo` на измеренно дорогое вычисление или на ссылку, без которой зависимости хука перезапускаются зря.

Мемоизация дешевле работы, которую она экономит, — это чистый проигрыш. Каждый render всё равно выделяет ячейку хука и сравнивает зависимости. `memo` ещё и сравнивает все props. «Я везде добавил `useCallback`» не является результатом профилирования. Аргумент — запись до и после на том же действии.

Серый или не отрисованный компонент в Profiler значит, что `memo` или внутренний bailout сработали. Это не список задач. Список задач — самые долгие коммиты на реальном сценарии: ввод в поиск, открытие строки, смена фильтра.

### На собеседовании

Сначала запись Profiler на конкретном действии, потом причина самого долгого куска. Чаще всего state или Context стоят слишком высоко. `memo` и `useCallback` ставят на измеренную границу, после стабилизации props. Дёшевый компонент мемоизация замедляет.

<a id="45-virtualization"></a>

## 45. Виртуализация списков

**Вопрос.** Когда список нельзя просто нарисовать целиком?

Когда иначе смонтировались бы сотни или тысячи строк. Виртуализатор рисует видимый срез плюс небольшой overscan и позиционирует эти строки внутри высокого контейнера. DOM остаётся маленьким. Прокрутка ощущается как полный список, потому что высота контейнера считается из числа строк.

Нужны стабильные key и либо фиксированная высота строки, либо измеренная. Переменная высота — трудная часть: библиотека меряет строку после кадра и поправляет смещение. Ошибка измерения дёргает скролл.

Виртуализация не ускоряет медленную строку. Она перестаёт создавать строки, которых пользователь не видит. Меню из двадцати пунктов виртуализировать не стоит: измерение и абсолютное позиционирование дороже самих строк. Строку сначала делают дешёвой. Если одна строка тянет тяжёлый график, окно из десяти таких строк всё равно будет тяжёлым.

Нельзя вешать на каждую строку эффекты, которые считают, что строка живёт, пока жив список. Строка размонтируется, как только уйдёт из overscan. Черновик внутри строки пропадёт, если он не поднят выше окна.

### На собеседовании

Окно рендерит видимые строки и небольшой запас, а не тысячи узлов. Нужны стабильные key и понятная высота. Это не оптимизация одной строки и не инструмент для короткого меню. State, который должен пережить прокрутку, в строке не держат: строка размонтируется, когда уходит с экрана.

<a id="46-security"></a>

## 46. Безопасность и `dangerouslySetInnerHTML`

**Вопрос.** Где React сам защищает от XSS и где эта защита кончается?

Строки в JSX экранируются. `<div>{userInput}</div>` не может вставить тег: угловые скобки станут текстом. Это защита по умолчанию для текста и для обычных атрибутов.

`dangerouslySetInnerHTML={{ __html: html }}` разбирает HTML и эту экранировку пропускает. Его используют для HTML, который уже прошёл санитайзер вроде DOMPurify, или для HTML, который вы собрали сами без пользовательских строк. Markdown от пользователя после превращения в HTML — это пользовательский HTML. Санитайзер ставят на результат, не на исходный текст, если рендерер может вернуть неожиданный тег.

Другие дыры, которые экранирование JSX не закрывает:

- `href={userUrl}` со значением `javascript:...`. Разрешают только `http`, `https` и относительные адреса.
- секрет в клиентском компоненте. Всё, что попало в браузерный бандл, публично.
- Server Action без проверки сессии. Это публичная точка входа, спрятанная кнопка авторизацией не является.
- сырой HTML в превью редактора.

`dangerouslySetInnerHTML` ещё и забирает этот кусок у обычных обновлений React. Если серверный HTML и клиентский разойдутся, получится mismatch при гидратации.

### На собеседовании

Текст в JSX React экранирует. `dangerouslySetInnerHTML` эту защиту выключает, поэтому HTML сначала очищают. Ссылки проверяют на протокол. Секреты не кладут в клиентский бандл. Серверное действие проверяет права внутри себя, а не рассчитывает на скрытую кнопку.

<a id="47-actions"></a>

## 47. Actions и form actions в React 19

**Вопрос.** Что такое Action и чем отправка формы через `action` отличается от `onSubmit`?

Action — функция, которую React умеет вести как transition, в том числе async-функция. У формы она получает `FormData`.

```jsx
async function createTask(formData) {
  await save(formData.get("title"));
}

<form action={createTask}>
  <input name="title" />
  <button type="submit">Добавить</button>
</form>
```

React оборачивает submit в transition. Форма остаётся интерактивной. Пока действие идёт, pending читает ребёнок формы:

```jsx
function Submit() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>Добавить</button>;
}
```

`useFormStatus` смотрит на родительский `<form>`. Вызов в том же компоненте, который этот `<form>` создаёт, ничего полезного не вернёт. Хук ставят в кнопку внутри формы.

Server Action с директивой `"use server"` выполняется на сервере. Его можно указать как `action` ещё до гидратации: форма отправится обычным POST. Это progressive enhancement. Функцию всё равно считают публичным endpoint. Сессию проверяют внутри. Поля `FormData` — пользовательский ввод, их валидируют на сервере. После записи вызывают revalidate пути или тега кэша, иначе следующий render увидит старые данные.

Клиентская функция, которую вы сами вызвали из `onSubmit` после `preventDefault`, — просто ваша функция. Transition вокруг неё сам не появится. Его задают через `startTransition` или через `useActionState`.

### На собеседовании

`action` формы получает `FormData`, а React ведёт async-отправку как transition. Pending читает `useFormStatus` изнутри формы, не снаружи. Server Action — публичная серверная функция: права проверяют внутри, кэш после записи инвалидируют. Ручной `onSubmit` этот переход сам не включает.

<a id="48-use-action-state"></a>

## 48. `useActionState`

**Вопрос.** Как связать результат формы, ошибку и флаг ожидания в одном месте?

`useActionState` соединяет action с куском state и с `isPending`. Action получает предыдущее состояние и данные формы, возвращает следующее.

```jsx
async function save(prev, formData) {
  const error = await updateName(formData.get("name"));
  if (error) return { ...prev, error };
  return { ok: true, error: null };
}

const [state, formAction, isPending] = useActionState(save, {
  ok: false,
  error: null,
});

return (
  <form action={formAction}>
    <input name="name" aria-invalid={Boolean(state.error)} />
    <button disabled={isPending}>Сохранить</button>
    {state.error && <p>{state.error}</p>}
  </form>
);
```

В отличие от `useFormStatus`, `isPending` доступен в том компоненте, который владеет формой. Третий аргумент, `permalink`, — адрес для отправки без JavaScript, когда action серверный. Возвращаемый state должен сериализоваться, если функция выполняется на сервере: туда нельзя положить класс ошибки или функцию.

Хук нужен, когда форма показывает результат или ошибку самого действия. Кнопке, которой интересен только `pending`, хватает `useFormStatus`. Тащить `useActionState` ради одной блокировки кнопки незачем.

Предыдущее состояние приходит первым аргументом, чтобы можно было накопить ошибки или не потерять поля, которые этот submit не менял. Игнорировать `prev` можно, но тогда каждый ответ должен быть полным новым состоянием.

### На собеседовании

`useActionState` даёт состояние формы, action для атрибута `action` и `isPending` в том же компоненте. Action считает следующее состояние из предыдущего и `FormData`. Для одной кнопки внутри формы достаточно `useFormStatus`. Состояние серверного action должно сериализоваться.

<a id="49-use-optimistic"></a>

## 49. `useOptimistic`

**Вопрос.** Как показать результат действия, пока запрос ещё идёт, и убрать его, если запрос упал?

`useOptimistic` хранит временное значение на время transition или action. Когда действие заканчивается, хук снова возвращает источник правды.

```jsx
const [optimisticName, setOptimisticName] = useOptimistic(name);

async function submit(formData) {
  const next = formData.get("name");
  setOptimisticName(String(next));
  await updateName(next);
}
```

Пока transition жив, `optimisticName` равен `next`. Когда `updateName` завершился, хук снова отдаёт `name`. Если родитель уже получил свежие props или свежий кэш, на экране остаётся сохранённое имя. Если запрос упал и `name` не изменился, UI откатывается сам: временная копия просто исчезает.

Сеттер вызывают внутри transition или action. Из обычного события без transition временному значению не к чему прикрепиться, и приём не работает как задумано.

Для списка есть форма с reducer:

```jsx
const [optimisticMessages, addMessage] = useOptimistic(
  messages,
  (current, message) => [...current, message],
);
```

Источник правды — `messages`. Оптимистичный список существует только на время отправки. Это заменяет россыпь флагов `isSaving` на счастливом пути. Ошибку действия всё равно надо нарисовать, если action её вернул: откат значения не объясняет пользователю, почему имя осталось старым.

Хук не заменяет сервер. Он не ретраит запрос и не мержит конфликт двух вкладок. Он только рисует ожидание.

### На собеседовании

`useOptimistic` показывает временное значение, пока идёт action, и возвращается к настоящему state, когда action закончился. Откат при ошибке получается сам, если источник правды не изменился. Сеттер вызывают внутри transition. Для списка передают reducer. Текст ошибки это не заменяет.

<a id="50-use-api"></a>

## 50. API `use`

**Вопрос.** Что читает `use` и почему промис нельзя создавать прямо в render?

`use(resource)` во время render читает promise или Context.

```jsx
const user = use(userPromise);
const theme = use(ThemeContext);
```

Если `userPromise` ещё выполняется, компонент приостанавливается. Ближайший `Suspense` показывает fallback. Если промис отклонён, ближайший error boundary получает ошибку. `use(context)` читает то же, что `useContext`, и его можно вызвать внутри `if`. Остальные хуки по-прежнему нельзя.

Промис должен быть стабильным между render. `use(fetch("/api/user"))` начинает новый запрос на каждый проход и подвешивает компонент навсегда: каждый render видит новый, ещё не завершённый промис. Промис кэшируют снаружи: в модуле, в loader роутера или в кэше фреймворка. В теле компонента его не создают.

Так клиентский компонент дочитывает промис, который заранее запустил Server Component и передал prop-ом. Сервер стартовал загрузку рано. Клиент ждёт тот же промис, без второго запроса и без эффекта.

`use` не заменяет `useEffect` для подписки на браузерное событие. Ему нужен thenable, который кто-то уже создал, или Context. Создавать запрос «при появлении компонента» по-прежнему можно эффектом с cleanup, если сервер этот запрос не начинал.

### На собеседовании

`use` читает promise или Context во время render. Незавершённый промис уходит в Suspense, отклонённый — в error boundary. Вызов может быть условным. Промис создают один раз снаружи компонента. `use(fetch())` в теле компонента запускает новый запрос на каждый render.

<a id="51-ref-cleanup"></a>

## 51. Ref как prop и cleanup ref в React 19

**Вопрос.** Зачем раньше был `forwardRef` и как теперь очищать подписку на DOM-узел?

В React 19 `ref` — обычный prop функционального компонента. `forwardRef` всё ещё работает, новым компонентам он не нужен.

```jsx
function Input({ ref, ...props }) {
  return <input ref={ref} {...props} />;
}
```

Родитель пишет `<Input ref={inputRef} />` и получает DOM-узел. Отдельная обёртка, чтобы пробросить ref мимо компонента, больше не нужна.

Колбэк ref может вернуть cleanup. React вызовет его, когда узел отсоединяют: перед следующим подключением и при unmount.

```jsx
<input
  ref={(node) => {
    const observer = new ResizeObserver(onResize);
    observer.observe(node);
    return () => observer.disconnect();
  }}
/>
```

Раньше тот же колбэк вызывали второй раз с `null`, и очистку писали в ветке `if (!node)`. Возвращаемая функция заменяет эту ветку. Из колбэка возвращают либо эту функцию, либо ничего. Неявный возврат узла, `ref={(node) => (el = node)}`, cleanup-ом не является. Тело колбэка пишут блоком, со скобками.

Колбэк ref выполняется после commit, когда DOM-узел уже есть. Мерить раскладку в render и складывать результат в ref вместо этого нельзя. Измерение, которое обязано случиться до кадра, остаётся в `useLayoutEffect`.

### На собеседовании

В React 19 `ref` передают как обычный prop, без `forwardRef`. Колбэк ref возвращает cleanup, и React вызывает его при отсоединении узла. Раньше для этого колбэк звали с `null`. Из колбэка не возвращают сам узел. Измерение до отрисовки кадра по-прежнему живёт в `useLayoutEffect`.
