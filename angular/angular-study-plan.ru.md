План для человека, который уже пишет на React. Каждый блок — это тема, вопросы и ответ, который можно сказать вслух. Короткие формулировки на английском лежат в [angular.md](angular.md), сложные follow-up — в [tricky-angular-interview-answers.md](tricky-angular-interview-answers.md). Термины Angular (`signal`, `OnPush`, `NgModule`, `pipe`, `injector`) оставлены на английском: так их и произносят.

## 1. Компоненты, шаблоны, binding

### Что такое компонент Angular?

Класс с декоратором `@Component`. В метаданных лежат `selector`, шаблон, стили и список `imports` того, чем шаблон пользуется. Angular компилирует шаблон заранее в инструкции, которые создают и обновляют DOM напрямую. Виртуального DOM нет: если binding изменился, обновляется конкретный узел.

В React компонент — функция, которая возвращает описание UI, а reconciliation сравнивает деревья. В Angular шаблон — отдельный язык, а «когда пересчитать» решает change detection, а не повторный вызов функции.

Скажи так: компонент связывает класс, шаблон и стили. Стили по умолчанию инкапсулированы (`ViewEncapsulation.Emulated`): селекторы переписываются атрибутами, чтобы не текли наружу. Хост-элемент по умолчанию `display: inline`, из-за этого часто ломается вёрстка, пока не поставишь `:host { display: block }`.

### Какие виды data binding есть?

| Синтаксис | Куда | Пример |
| --- | --- | --- |
| `{{ expr }}` | Класс → текст в DOM, всегда экранируется | `{{ user().name }}` |
| `[prop]="expr"` | Класс → DOM-свойство или input ребёнка | `[disabled]="saving()"` |
| `(event)="handler($event)"` | Событие DOM или output ребёнка → класс | `(click)="save()"` |
| `[(value)]="sig"` | Туда и обратно: свойство плюс событие `valueChange` | `[(ngModel)]="name"` |
| `[attr.x]`, `[class.x]`, `[style.x.px]` | Атрибут, класс, стиль | `[attr.aria-label]="label"` |

Property binding пишет в **свойство** DOM, не в HTML-атрибут. У `colspan` нет свойства, поэтому нужен `[attr.colspan]`. Интерполяция безопасна от XSS: значение экранируется. `[innerHTML]` уже проходит санитизацию и это другая история.

Двусторонняя запись `[(value)]` — это сахар для `[value]` плюс `(valueChange)`. Её называют banana in a box.

## 2. Standalone и NgModules

### Что изменилось со standalone-компонентами?

Компонент сам объявляет зависимости шаблона в `imports`. Отдельный NgModule для этого не нужен. В свежих версиях standalone — значение по умолчанию, флаг `standalone: true` можно не писать.

Приложение стартует через `bootstrapApplication(AppComponent, { providers: [...] })`. Фичи подключаются функциями `provideX()`: `provideRouter`, `provideHttpClient`, `provideZonelessChangeDetection`.

Скажи так: единица компиляции теперь сам компонент, а не модуль. Ленивая загрузка — `loadComponent` для одной страницы и `loadChildren` для набора дочерних роутов.

### Что делали NgModule и зачем их ещё знать?

NgModule собирал `declarations` (компоненты, директивы, pipes), `imports`, `exports` и `providers` и задавал контекст компиляции. В больших старых приложениях они никуда не делись.

Два факта, которые спрашивают:

- `forRoot()` / `forChild()`: один модуль, разные провайдеры для корня и для ленивой фичи. `forRoot` регистрирует синглтон один раз, `forChild` не создаёт второй.
- `providers` внутри lazy-модуля создают дочерний injector. Сервис там — отдельный экземпляр, не корневой синглтон.

Миграция инкрементальная: схематик `ng generate @angular/core:standalone`, потом control flow, потом signal inputs. Не big-bang.

## 3. Как компоненты общаются

Четыре канала.

- Родитель → ребёнок: `input()` или `input.required()`. Старый вид — `@Input()`.
- Ребёнок → родитель: `output()`. Старый вид — `@Output() x = new EventEmitter<T>()`.
- Туда и обратно: `model()` у ребёнка, у родителя `[(value)]="signalOrField"`.
- Соседи и далёкие части дерева: общий сервис, обычно на signals, или store.

Signal input — это read-only signal. Производные значения считают через `computed()`, а не через `ngOnChanges`. Обязательный input проверяется на этапе компиляции. Читать `input.required()` в конструкторе нельзя: значение ещё не установлено, будет ошибка. Читай его в `computed`, в `effect` или в шаблоне.

`transform` приводит строку атрибута к типу: `disabled = input(false, { transform: booleanAttribute })`.

`model()` создаёт записываемый signal и неявный output `<name>Change`. Когда ребёнок делает `expanded.update(...)`, родитель получает событие. Это уместно для открыто/закрыто, выбранной вкладки, значения своего контрола. Если двусторонней привязки слишком много, поток данных перестаёт читаться. Та же претензия, что к uncontrolled-компонентам в React.

`output()` не обязан быть `EventEmitter`. Это просто канал «ребёнок сказал родителю». Для состояния между несвязанными компонентами output не тяни через пять уровней: положи signal в сервис.

## 4. Шаблон: control flow, defer, директивы, pipes

### Что заменило `*ngIf` и `*ngFor`?

Встроенные блоки. Их не надо импортировать.

```html
@if (user(); as u) {
  <p>{{ u.name }}</p>
} @else {
  <p>Guest</p>
}

@for (item of items(); track item.id; let i = $index) {
  <app-row [item]="item" />
} @empty {
  <p>Nothing here</p>
}

@switch (status()) {
  @case ('loading') { <app-spinner /> }
  @default { <app-content /> }
}

@let total = items().length;
```

`track` обязателен и работает как `key` в React. Старые `*ngIf` и `*ngFor` живы, в легаси их полно.

`track item.id` — стабильный идентификатор. `track item` сравнивает ссылку на объект: после повторного запроса с сервера все объекты новые, Angular уничтожает и создаёт весь список заново, теряются фокус и раскрытые строки. `track $index` нормален для статичного списка без своего состояния. Если элементы вставляют и удаляют, состояние строки прилипнет не к той записи. Та же ошибка, что index-key в React.

Вызов функции в шаблоне (`{{ format(row) }}`) выполняется на **каждом** проходе change detection, на каждой строке. Геттер ведёт себя так же. Форматирование — pure pipe или `computed`. Вызов signal (`{{ count() }}`) дешёвый: это чтение мемоизированного значения, не произвольный расчёт.

### Что делает `@defer`?

Лениво грузит кусок шаблона отдельным чанком, когда срабатывает триггер: `on viewport`, `on idle` (по умолчанию), `on interaction`, `on hover`, `on timer(2s)`, `on immediate` или `when condition`. Рядом бывают `@placeholder`, `@loading`, `@error` и `prefetch on …`.

```html
@defer (on viewport; prefetch on idle) {
  <app-flame-graph [data]="trace()" />
} @placeholder (minimum 300ms) {
  <div class="skeleton"></div>
} @loading (after 150ms; minimum 500ms) {
  <app-spinner />
} @error {
  <p>Failed to load</p>
}
```

Ловушки:

- Всё внутри должно быть standalone и **нигде больше не упоминаться в том же файле**, включая TypeScript. Иначе бандлер затянет это сразу, и откладывать будет нечего.
- `on viewport` нужен placeholder или элемент, за которым можно наблюдать.
- Без `minimum` и `after` быстрая загрузка мигает спиннером.
- На сервере `@defer` рисует placeholder. При инкрементальной гидратации (`hydrate on viewport`) сервер рисует настоящий контент и гидратирует его позже.

### Какие бывают директивы?

- **Компонент** — директива с шаблоном.
- **Атрибутная** меняет поведение или вид существующего элемента: `appTooltip`, `appAutofocus`, `ngClass`.
- **Структурная** добавляет или убирает шаблон: `*ngIf`, `*ngFor`, свой `*appHasRole`. Внутри `TemplateRef` и `ViewContainerRef`.
- **Host directive** (`hostDirectives`) подмешивает поведение директивы в компонент без наследования.

Звёздочка — сахар над `ng-template`. `*ngFor="let item of items"` разворачивается в `<ng-template ngFor [ngForOf]="items">`. Две структурные директивы на один элемент повесить нельзя. Оборачивают в `ng-container` или пишут блоки `@if` / `@for`, которые вкладываются естественно.

Слушатели и привязки к хосту в новом коде пишут объектом `host`, не декораторами `@HostBinding` / `@HostListener`. Глобальные слушатели `window:` и `document:` снимаются при уничтожении компонента. В приложении с Zone.js `window:scroll` на каждый пиксель запускает change detection. Такое уводят в `NgZone.runOutsideAngular`.

### Что такое pipe и что значит pure?

Pipe преобразует значение в шаблоне: `{{ price | currency: 'EUR' }}`. **Pure** (по умолчанию) пересчитывается, только когда сменилась ссылка на вход или аргумент. Это мемоизированная функция. **Impure** (`pure: false`) бежит на каждом проходе change detection. `async` impure, потому что должен заметить новую эмиссию.

Мутация массива через `push` не меняет ссылку, pure pipe не перезапустится, на экране старое значение. Тяжёлую фильтрацию лучше считать в `computed` в классе: проще тестировать. Pure pipe оставляй для форматирования.

`async` pipe подписывается на Observable или Promise, отдаёт последнее значение, на каждой эмиссии зовёт `markForCheck()` (поэтому работает с OnPush) и отписывается при уничтожении. До первой эмиссии значение `null`.

Каждый `| async` — **отдельная подписка**. На cold HTTP Observable это отдельный запрос:

```html
<h1>{{ (user$ | async)?.name }}</h1>
<img [src]="(user$ | async)?.avatar" />
```

Лечится одним `@if (user$ | async; as user)`, либо `toSignal` в классе, либо `shareReplay` на источнике.

### Как передать разметку внутрь компонента?

`<ng-content>` — аналог `children`. Несколько слотов выбирают через `select`:

```html
<header><ng-content select="[card-title]" /></header>
<ng-content />
```

| | Рисует DOM? | Зачем |
| --- | --- | --- |
| `ng-template` | Нет, пока кто-то не создаст view | Чертёж. Структурные директивы, `ngTemplateOutlet`, ветка `@else` |
| `ng-container` | Своего элемента нет | Группировка без лишнего `div`, как Fragment |
| `ng-content` | Переносит сюда узлы родителя | Слот для контента родителя |

Спроецированный контент принадлежит **view родителя**, не ребёнка. Если в шаблоне ребёнка написано `@if (open()) { <ng-content /> }`, тяжёлый график внутри всё равно создаётся, его `ngOnInit` и HTTP уходят, даже когда панель закрыта. `@if` вокруг `ng-content` только прячет DOM. Один и тот же контент нельзя вставить в два `ng-content`.

Если контент должен появляться по условию, родитель передаёт `ng-template`, а ребёнок рисует его через `ngTemplateOutlet` только когда нужно. Либо `@defer`.

### Чем `viewChild` отличается от `contentChild`?

`viewChild` ищет в **своём** шаблоне. `contentChild` ищет то, что **спроецировал родитель**. Сигнальные версии (`viewChild()`, `viewChildren()`, `contentChild()`, `contentChildren()`) обновляются сами, когда элемент появляется и исчезает. Декораторы `@ViewChild` / `@ContentChild` доступны после `ngAfterViewInit` / `ngAfterContentInit`.

`{ static: true }` у декоратора резолвится до `ngOnInit`, но только если элемент не внутри `@if` / `*ngIf`. То, что может не существовать, static быть не может. `viewChild.required()` бросает, если прочитать его слишком рано. Читай в `afterNextRender`, в `effect` или в обработчике.

### В каком порядке идут lifecycle-хуки?

`constructor` → `ngOnChanges` (когда выставлены inputs) → `ngOnInit` → `ngDoCheck` → `ngAfterContentInit` → `ngAfterContentChecked` → `ngAfterViewInit` → `ngAfterViewChecked` → на обновлениях повторяются check-хуки → `ngOnDestroy`.

У родителя `P` и ребёнка `C` на первом проходе view родителя инициализируется **после** view всех детей. Поэтому `@ViewChild` готов в `ngAfterViewInit` родителя, и поэтому менять там состояние, которое шаблон родителя уже отрисовал, даёт `ExpressionChangedAfterItHasBeenCheckedError`.

`ngDoCheck` и хуки `*Checked` бегут на **каждом** проходе. Тяжёлый код там — запах по производительности.

Конструктор — момент, когда DI создал экземпляр. Inputs ещё нет. Туда (или в инициализаторы полей) кладут `inject()`, создание signals и регистрацию effects. `ngOnInit` — один раз после первого `ngOnChanges`, когда декораторные inputs уже есть. С signal inputs «подождать input» почти всегда становится `computed` или `effect`, и `ngOnInit` нужен реже. HTTP и тяжёлую работу в конструктор не клади: в тестах компонент часто создают и тут же выбрасывают.

Современные замены:

- Производное состояние: `computed()` вместо `ngOnChanges`.
- Отписка: `inject(DestroyRef).onDestroy(...)` или `takeUntilDestroyed()`.
- Работа с DOM после отрисовки: `afterNextRender()` один раз и `afterEveryRender()` на каждый рендер. Для SSR они безопасны: бегут только в браузере.

## 5. Signals

### Что такое signals?

Синхронные реактивные значения. Когда значение меняется, об этом узнают те, кто его прочитал. Обновления мелкозернистые и без глитчей: за один тик читатель видит согласованное состояние, а не промежуточное.

```ts
const count = signal(0);
const double = computed(() => count() * 2);
effect(() => console.log(double()));
count.update(c => c + 1);
```

- `signal` — записываемое состояние: `set`, `update`, `asReadonly`.
- `computed` — производное, только чтение, кэш, пока зависимость не изменилась.
- `effect` — побочный эффект наружу: localStorage, лог, императивная библиотека.
- `linkedSignal` — записываемое состояние, которое сбрасывается, когда меняется источник.
- `resource` / `httpResource` / `rxResource` — асинхронные данные как signals.
- `untracked` — прочитать signal, не подписавшись на него.

Аналогии с React: `signal` ≈ `useState`, `computed` ≈ `useMemo` с автоматическими зависимостями, `effect` ≈ `useEffect`, но зависимости тоже снимаются автоматически.

### Равенство и иммутабельность

Signal уведомляет, только если новое значение **не равно** старому. По умолчанию сравнение — `Object.is`.

```ts
items().push('a');                    // мутация: уведомления нет, computed врёт
items.update(list => [...list, 'a']); // новый массив: уведомление есть
```

`computed` тоже сравнивает результат. Если пересчёт дал равное значение, зависимые не уведомляются. `computed(() => logs().length > 0)` отсекает лишнюю волну обновлений.

Своё равенство передают опцией `equal`.

### `computed`: ленивость и динамические зависимости

Не считается, пока кто-то не прочитал. Мемоизируется, пока зависимость не изменилась. Зависимости динамические: трекаются только signals, прочитанные при **последнем** выполнении.

Если `showDetails()` ложно и внутри тернарника `details()` не читается, изменение `details` не пересчитает `computed`. Это правильно и дёшево. «Подписаться заранее» условным чтением нельзя.

Побочные эффекты внутри `computed` (HTTP, запись в другой signal) запрещены по смыслу. Это чистый вывод. Эффекты — в `effect` или в обработчике события.

### `effect`: когда и когда нет

Effects бегут **асинхронно**, как часть change detection, не синхронно на `set()`. Несколько `set` подряд дают один запуск. Effect, созданный в компоненте, умирает вместе с ним. Вне injection context нужно передать `injector`.

Cleanup: `effect((onCleanup) => { const id = setInterval(tick, 1000); onCleanup(() => clearInterval(id)); })`.

Хорошо: localStorage, аналитика, график, карта, `document.title`.

Плохо, и это классический вопрос:

```ts
effect(() => this.fullName.set(`${this.first()} ${this.last()}`)); // нет
fullName = computed(() => `${this.first()} ${this.last()}`);       // да
```

Запись в signal из effect даёт лишние циклы change detection и может зациклиться. Это Angular-версия «вам, возможно, не нужен effect».

`untracked(() => signal())` читает значение без зависимости. В effect один signal должен **запускать** перезапуск, другой только **прочитаться**. Без `untracked` чтение signals внутри вызванного метода сервиса тихо станет зависимостью.

### `linkedSignal`, `computed`, `effect`

| Нужно | Бери |
| --- | --- |
| Значение целиком выводится из других signals, только чтение | `computed` |
| Значение по умолчанию из источника, но пользователь может переопределить, и оно сбросится, когда источник изменится | `linkedSignal` |
| Побочный эффект вне графа signals | `effect` |

Пример: список опций пришёл новый, выбранный элемент сбрасывается на первый, но `selected.set(s)` по клику всё ещё работает. Раньше это писали effect-ом «сбросить выбор, когда список изменился». Это как раз антипаттерн выше.

### Signals и RxJS

Signals держат **состояние**: текущее значение, которое читает шаблон. RxJS описывает **события во времени**: debounce, отмена, retry, склейка асинхронных источников, websocket. Мост — `toSignal()` и `toObservable()`.

`toSignal(obs$)` подписывается **сразу** при создании. Cold HTTP Observable отправит запрос немедленно. Нужен injection context, отписка случится при уничтожении этого контекста. Без `initialValue` тип включает `undefined`. `requireSync: true` требует синхронную первую эмиссию (`BehaviorSubject`). Если поток падает с ошибкой, чтение signal бросает. Ошибку обрабатывай в потоке.

`toObservable(sig)` эмитит через effect, поэтому эмиссии **асинхронные и схлопываются**: `set(1); set(2); set(3)` в одном тике даст только `3`. Первое значение тоже уходит не в момент subscribe.

### Асинхронные данные: `resource` и `httpResource`

`resource` превращает загрузку в signals. Когда signal с параметрами меняется, вызывается loader, предыдущий запрос отменяется, снаружи есть `value()`, `isLoading()`, `error()`, `status()`, `reload()`.

```ts
user = httpResource<User>(() => `/api/users/${this.userId()}`);
```

API молодой, имена опций между версиями менялись (`request` стал `params`). На собеседовании объясняй идею: загрузка, которой управляет signal, и встроенная защита от гонки. Сложные потоки (debounce, retry, websocket) по-прежнему удобнее на RxJS, мост — `rxResource`.

## 6. Dependency injection

### Как устроен DI?

Классы и значения регистрируют провайдерами и запрашивают через `inject()` или параметры конструктора. Angular создаёт экземпляры и кэширует их в **injectors**.

```ts
@Injectable({ providedIn: 'root' })
export class UsersApi {
  private http = inject(HttpClient);
  getUser(id: string) { return this.http.get<User>(`/api/users/${id}`); }
}
```

`inject()` работает только в injection context: инициализаторы полей и конструкторы классов, которые создаёт DI; `useFactory`; функциональные guards, resolvers, interceptors; `runInInjectionContext`. Вызов в `ngOnInit` даёт `NG0203`. То же ограничение у `toSignal`, `takeUntilDestroyed()` без аргумента, `effect`, `afterNextRender`.

`inject()` лучше конструктора, когда код — функция: guard, interceptor, хелпер `injectX()`, похожий на custom hook. С наследованием и выводом типов тоже проще.

### Два дерева инжекторов

1. **Element injectors.** Их создают `providers` на компонентах и директивах. Один экземпляр на экземпляр компонента, виден поддереву.
2. **Environment injectors.** Корень (`providedIn: 'root'`, провайдеры `bootstrapApplication`) и уровень роута (`providers` на ленивом роуте).
3. Дальше platform и null injector, который бросает `NullInjectorError`.

Поиск `inject(X)` из компонента идёт вверх по element injectors, потом в environment injector этого view (роут → корень) → platform → ошибка.

Десять виджетов с `providers: [WidgetStore]` получают десять независимых store. Каждый умрёт вместе с виджетом, дети виджета получат именно его store. Так состояние ограничивают поддеревом без глобального синглтона.

### Почему «синглтон» оказывается в двух экземплярах

1. Сервис указан и в `providedIn: 'root'`, и в `providers` компонента. У компонента своя копия.
2. Сервис в `providers` ленивого роута или модуля. Дочерний environment injector, отдельный экземпляр на фичу.
3. Старый NgModule: модуль с `providers` импортирован в несколько lazy-модулей. От этого и существует `forRoot()`.

Настоящий синглтон: `@Injectable({ providedIn: 'root' })` и больше нигде. На компоненте или роуте регистрируй только когда отдельный экземпляр нужен сознательно.

### Модификаторы поиска

- `optional: true` — `null`, если провайдера нет, вместо исключения.
- `self: true` — только injector этого элемента. Контрол формы, который обязан лежать на том же теге.
- `skipSelf: true` — начать с родителя. Рекурсивное дерево ищет родительский узел.
- `host: true` — остановиться на границе хост-компонента.

Декораторы-близнецы: `@Optional()`, `@Self()`, `@SkipSelf()`, `@Host()`.

### Типы провайдеров

- `useClass` — новый экземпляр другого класса.
- `useValue` — готовое значение.
- `useFactory` — функция, внутри можно звать `inject()`.
- `useExisting` — псевдоним **того же** экземпляра.
- `multi: true` — несколько значений под одним токеном, `inject` вернёт массив.

`useClass` вместо `useExisting` создаёт второй экземпляр со своим состоянием. `InjectionToken` нужен для того, что не является классом: конфиг, функция, интерфейс. Интерфейса TypeScript в рантайме нет, по нему искать нечего.

### `providers` и `viewProviders`

Оба кладут провайдеры в element injector компонента. Разница — спроецированный контент.

- `providers` виден и своему шаблону, и тому, что пришло через `<ng-content>`.
- `viewProviders` виден только своему шаблону.

`viewProviders` нужен автору библиотеки, чтобы внутренний сервис не протекал в контент, который подставит потребитель.

## 7. Change detection

Это блок, который стоит проговорить вслух целиком.

### Как Angular понимает, что view пора обновить?

**С Zone.js, классика.** Zone.js патчит асинхронные API браузера: события DOM, `setTimeout`, `Promise`, XHR и fetch. Когда асинхронная задача закончилась, Zone говорит Angular «что-то могло измениться», и бежит `ApplicationRef.tick()`. Дерево обходится от корня, каждый binding сравнивается с прошлым значением, в DOM пишется только разница.

Angular не знает, **что** изменилось. Он знает, что случилось **что-то асинхронное**, и при стратегии по умолчанию проверяет всё. Один binding дёшев. Дерево на каждый `mousemove` — нет. Виртуального DOM нет. В dev-режиме после прохода идёт второй проверочный. Из него растёт `ExpressionChangedAfterItHasBeenCheckedError`.

**OnPush.** Компонент и его поддерево пропускают, если не случилось одно из четырёх:

1. Input сменился **по ссылке**.
2. Событие сработало в его шаблоне или в шаблоне ребёнка.
3. Позвали `markForCheck()`. Так делает `async` pipe на каждой эмиссии.
4. Изменился signal, прочитанный в шаблоне.

Ловушка: `this.filters.tags.push(tag)` оставляет ту же ссылку, OnPush-ребёнок не обновится. Нужен новый объект: `this.filters = { ...this.filters, tags: [...this.filters.tags, tag] }`. До OnPush мутацию ловила глобальная проверка, поэтому «раньше работало». Signals делают иммутабельность естественной: уведомление есть только у `set` / `update` с новым значением.

**Zoneless** (`provideZonelessChangeDetection()`, у новых приложений в свежих версиях это дефолт). Zone.js нет. Change detection планируется только когда об этом попросили: изменился signal в шаблоне, позвали `markForCheck`, сработало событие шаблона, изменился input через `setInput`. Меньше бандл, нет monkey-patch, нет холостых проверок от чужих таймеров, читаемые стеки, нативный `async/await` без транспиляции.

При миграции ломается запись в обычное поле из таймера, промиса или ручной подписки: view не обновится. `this.loading = false` надо заменить на `this.loading.set(false)`. Ломается код на `NgZone.onStable` / `onMicrotaskEmpty` и тесты на `fakeAsync`, которые предполагали Zone. Путь: сначала OnPush везде, состояние в signals или `async` pipe, потом выключать Zone.

### `markForCheck`, `detectChanges`, `detach`

- `markForCheck()` помечает этот компонент **и предков** грязными. Сразу ничего не бежит, их проверят на следующем проходе. Нужен, когда данные OnPush-компонента изменились вне знания Angular, например в ручной подписке.
- `detectChanges()` **синхронно** проверяет этот компонент и детей прямо сейчас. После `detach()` или когда DOM обязан обновиться до следующей строки. Редкий инструмент.
- `detach()` вынимает компонент из автоматических проверок. Дальше сам зовёшь `detectChanges()`, например раз в кадр для очень горячего виджета.

Звать `detectChanges()` «чтобы починить» устаревший view — значит прятать сломанный поток данных. Так же легко поймать `ExpressionChanged`.

### `ExpressionChangedAfterItHasBeenCheckedError`

Только dev-режим. После прохода Angular прогоняет проверку ещё раз. Если binding уже другой, данные изменились **во время** проверки, и view показал бы устаревшее.

Обычные причины: запись состояния в `ngAfterViewInit` / `ngAfterViewChecked`, которую шаблон уже отрисовал; ребёнок меняет значение родителя во время проверки; геттер, который каждый раз возвращает новое (`Date.now()`, новый массив или объект).

Чиню раньше по потоку: посчитать значение в конструкторе, `ngOnInit` или `computed`, либо перенести логику в событие. `setTimeout` и лишний `detectChanges` гасят ошибку и оставляют поток кривым. Так и скажи.

### Код вне Angular и Zone.js

В приложении с Zone каждый слушатель события запускает полную проверку. Для `mousemove`, `scroll`, `resize`, `requestAnimationFrame`, websocket и чартов это пустая работа. `NgZone.runOutsideAngular` вешает слушатели так, что они проверку не будят. Обратно в Angular заходят через `zone.run(...)` только когда UI правда должен обновиться.

«Zone pollution» — сторонняя библиотека будит change detection слишком часто. Angular DevTools показывает это как много крошечных циклов. В zoneless этого почти нет.

Zone.js не может пропатчить нативный `async/await`: движок обрабатывает его внутри, не через `Promise.prototype.then`. Поэтому сборка с Zone.js **опускает async/await до генераторов**. Если в современном таргете в бандле видны генераторы, причина в этом. Zoneless-приложению даунлевел не нужен.

### Как это сказать React-разработчику за минуту

В React обновление перерисовывает компоненты и сверяет virtual DOM. В Angular с Zone.js любое асинхронное событие запускает обход дерева и сравнение bindings. OnPush — ближайший родственник `React.memo`: проверяем, только если сменилась ссылка на input, событие, signal или `markForCheck`. Zoneless убирает «проверить всё на всякий случай» и оставляет явные уведомления, в первую очередь от signals.

## 8. Роутер

Ленивая загрузка: `loadComponent` на один компонент, `loadChildren` на набор дочерних роутов. Функциональные guards: `canActivate`, `canActivateChild`, `canDeactivate`, `canMatch`. Resolver prefetch-ит данные до активации. Параметры читают из `ActivatedRoute.paramMap` / `queryParamMap` или биндят во inputs через `withComponentInputBinding()`. `providers` на роуте дают сервисы в области фичи.

### `canMatch` и `canActivate`

`canActivate` отвечает на вопрос «роут уже совпал, можно ли его активировать?». `canMatch` отвечает раньше: «этот роут вообще может совпасть?». Если нет, роутер пробует **следующий роут с тем же путём**, и ленивый чанк не скачивается.

Так делают флаги фич и разные варианты одного URL для разных ролей. Старый `canLoad` для этого устарел. Guards — это UX, не безопасность. Бэкенд всё равно авторизует каждый запрос.

### Resolver или загрузка в компоненте?

Resolver приносит данные **до** завершения навигации. Компонент получает их синхронно и не держит свой loading. Цена: клик ничего не показывает, пока данные не пришли. Медленный API замораживает приложение. Ошибку надо обработать в resolver или редиректом.

Senior-ответ: resolver для маленьких критичных данных (права, «сущность есть, иначе 404»). Тяжёлые данные — сразу перейти на страницу и грузить в компоненте или store со скелетоном. Если resolver всё же есть, верхний прогресс по событиям роутера.

### Повторное использование роута и устаревший snapshot

Переход с `/trace/1` на `/trace/2` **переиспользует** тот же экземпляр: конфиг роута тот же, сменился параметр. Конструктор и `ngOnInit` не бегут снова. `this.route.snapshot.paramMap.get('id')`, прочитанный в `ngOnInit`, навсегда останется `"1"`.

Рабочие варианты: `input()` вместе с `withComponentInputBinding()` (обновляется на каждой навигации) и `httpResource` от этого id, либо `paramMap.pipe(switchMap(...))`. Свой `RouteReuseStrategy` может держать компонент живым между роутами, например страницу поиска при возврате назад. Цена — память и устаревшие данные.

## 9. Формы

### Reactive и template-driven

- **Reactive** (`FormControl`, `FormGroup`, `FormArray`, `FormRecord`): модель в классе, типы, тестируемость, сложные и динамические формы. Изменения значения — Observable `valueChanges`.
- **Template-driven** (`ngModel`): модель в шаблоне. Проще для маленькой формы, тяжело тестировать и строить динамически.
- **Signal forms**: экспериментальный API на signals в самых новых версиях. Идею знай, в проде большой кодовой базы её может ещё не быть.

Формы типизированы. `FormControl` по умолчанию имеет тип `string | null`, потому что `reset()` ставит `null`. `nonNullable: true` или `NonNullableFormBuilder` возвращают `reset()` к начальному значению, и тип становится `string`.

**Выключенные контролы не входят в `form.value`.** Для сабмита нужен `form.getRawValue()`. Это классический баг. `valueChanges` стреляет и на программный `setValue`. Чтобы не зациклиться, передают `{ emitEvent: false }`. `FormRecord` — динамические ключи, `FormArray` — динамический список.

### Свой input и `ControlValueAccessor`

Мост, благодаря которому свой компонент ведёт себя как нативный input с `formControlName` или `ngModel`. Четыре метода: `writeValue` (модель → view, **не** звать здесь `onChange`), `registerOnChange`, `registerOnTouched`, `setDisabledState`. Провайдер — `NG_VALUE_ACCESSOR` с `useExisting` и `multi: true`.

Ловушки: `onChange` внутри `writeValue` помечает форму dirty при загрузке; без `setDisabledState` вызов `control.disable()` ничего не делает на экране; без `onTouched` ломается «показать ошибку по blur». Свою валидацию добавляют ещё и провайдером `NG_VALIDATORS`.

### Async-валидаторы и `updateOn`

Синхронные валидаторы бегут первыми. Асинхронные стартуют, только если синхронные прошли. Пока они бегут, статус `PENDING`, сабмит лучше держать выключенным. Новый Observable на каждый символ отменяет предыдущий, если оператор это умеет (`switchMap`). `timer(300)` даёт debounce. `updateOn: 'blur'` или `'submit'` снижает шум валидации и `valueChanges`.

## 10. HTTP и RxJS

### Как работает `HttpClient`?

Возвращает **cold** Observable: запрос уходит на subscribe, каждая подписка шлёт новый запрос, отписка отменяет его. Подключение: `provideHttpClient(withInterceptors([...]), withFetch())`.

`shareReplay({ bufferSize: 1, refCount: false })` кэширует разовые данные вроде конфига навсегда. `refCount: true` отписывается от источника, когда ушёл последний подписчик. `shareReplay` кэширует и **ошибки**, пока не подпишутся заново. `catchError` ставь до него, либо делай кэш, который можно сбросить.

### Зачем interceptors?

Сквозная логика запроса и ответа: заголовок авторизации, retry, ошибки, лог, кэш, correlation id. В современном Angular это функции `HttpInterceptorFn`. Запрос иммутабелен, всегда `req.clone({...})`.

Порядок в `withInterceptors([auth, retry, logging])`: запрос идёт `auth → retry → logging → бэкенд`, ответ возвращается **в обратном порядке**. Retry после auth повторит запрос уже с заголовком. Retry до auth повторит всю цепочку, включая обновление токена.

`HttpContext` передаёт метаданные конкретному запросу, не засоряя заголовки. Например токен «не показывать тост на эту ошибку».

### Где Angular использует RxJS?

`HttpClient`, события и параметры роутера, `valueChanges` форм, `EventEmitter` (под капотом Subject), NgRx. Операторы, которые надо уметь объяснить: `switchMap`, `mergeMap`, `concatMap`, `exhaustMap`, `debounceTime`, `distinctUntilChanged`, `combineLatest`, `catchError`, `shareReplay`. Отписка: `async` pipe, `toSignal`, `takeUntilDestroyed`.

| Оператор | Когда |
| --- | --- |
| `switchMap` | Параметр роута → сущность; поиск → результаты. Старый запрос отменяется |
| `mergeMap` | Независимые детали пачкой, параллельно |
| `concatMap` | Сохранения по порядку, очередь мутаций |
| `exhaustMap` | Сабмит, логин, refresh: клики, пока занято, игнорируются |

`mergeMap` на поиске даёт гонку: медленный старый ответ затирает новый. `switchMap` на сохранении может отменить запрос, который сервер уже принял.

Вложенные `subscribe` не отменяют предыдущее (быстрая навигация показывает команду чужого пользователя), текут, не имеют одного места для ошибки и плохо тестируются. Разворачивай в `switchMap`.

Утекают подписки на потоки, которые сами не завершаются: select из store, `interval`, `fromEvent`, события роутера, `valueChanges`, Subject, websocket. `HttpClient` после одного ответа завершается, но отменится при уничтожении компонента только если ты отписался.

`takeUntilDestroyed` ставь **последним** оператором. Если он стоит до `switchMap`, внутренний поток опроса переживёт уничтожение компонента. Предпочтение: `async` pipe или `toSignal`, потом `takeUntilDestroyed()`, потом ручной `unsubscribe` в `DestroyRef.onDestroy`.

## 11. Состояние

| Вариант | Когда |
| --- | --- |
| Signals в компоненте | Локальный UI |
| Сервис с `@Injectable` и signals | Общее состояние фичи. Дефолт для большинства приложений |
| NgRx SignalStore | Структурный store с меньшим бойлерплейтом. Можно ограничить компонентом или роутом |
| NgRx Store (Redux) + Effects | Большое приложение, много фич реагируют на одни события, нужны devtools |
| URL, query-параметры роутера | То, чем делятся: фильтры, вкладки, выбор |

### NgRx: цикл

Компонент **диспатчит action** → **reducer** (чистая функция) считает новое состояние → **selectors** отдают мемоизированные срезы → компоненты читают их → **effects** слушают actions, делают побочные эффекты (HTTP) и диспатчат новые actions.

- Actions — это события, не команды: `[Search Page] Query Submitted`, не `setLoading`. Источник в скобках помогает в логе. Одну action не переиспользуй из десяти мест.
- Reducer чистый и синхронный: без HTTP, без `Date.now()`, без мутации.
- Selector мемоизирован. Производные данные живут в selector, не в state. `store.selectSignal()` возвращает signal.
- В effect оператор выбирают сознательно: `switchMap` для поиска, `concatMap` для сохранений по порядку, `exhaustMap` для логина.
- Коллекции нормализуют через `@ngrx/entity`.

Ошибку лови **внутри** flattening-оператора и превращай в failure action. `catchError` на внешнем потоке завершает effect на первой ошибке. Effect, который ничего не диспатчит, помечают `{ dispatch: false }`, иначе он задиспатчит свой вход обратно и зациклится.

NgRx лишний, когда состояние локально для одной фичи, приложение маленькое, «состояние» на самом деле кэш сервера, или команда ещё не держит RxJS. Файлов (actions, reducer, effects, selectors) становится много ради одного запроса.

Он уместен, когда много фич реагируют на одни события, сложный async хочется видеть в логе и devtools, большой команде нужны жёсткие договорённости, или нужны undo и оптимистичные обновления с откатом.

Фраза: «Начинаю с signals в сервисах, по сервису на фичу. NgRx или SignalStore подключаю там, где общая событийная сложность уже настоящая. Важнее единообразие в кодовой базе, чем выбор библиотеки.»

### NgRx SignalStore

Store на signals из собираемых фич: `withState`, `withComputed`, `withMethods`, `withHooks`. Бойлерплейта меньше, чем у Redux. Провайдится в root, на роуте или на компоненте. Свои фичи переиспользуются (`withEntities`, свой `withRequestStatus`). RxJS подключается точечно через `rxMethod`.

## 12. Производительность

Рычаги, которые стоит перечислить пачкой:

- OnPush везде и иммутабельные данные.
- Signals вместо ручного `markForCheck`.
- `track` в каждом `@for`.
- Никаких функций в шаблоне: pure pipe или `computed`.
- Ленивые роуты и `@defer`.
- CDK virtual scroll для длинных списков.
- В приложении с Zone.js — `NgZone.runOutsideAngular` для частых событий.
- Web Worker для тяжёлого счёта.
- Zoneless.
- Бюджеты бандла в `angular.json`.
- Профилирование в Angular DevTools.

Angular DevTools показывает дерево компонентов, inputs, outputs, значения signals и дерево инжекторов (откуда взялся провайдер, удобно ловить «два инстанса»). Профайлер показывает каждый цикл change detection, что его запустило и сколько занял компонент. Много циклов в секунду — zone pollution. Компонент, который долго считается каждый цикл, — вызовы методов в шаблоне или тяжёлый `ngDoCheck`.

Порядок рассказа: воспроизвёл → записал → нашёл горячий компонент или триггер → починил → измерил снова. Рядом смотри Performance и Memory в браузере: layout, paint, оторванные DOM-узлы.

### Виртуальный скролл

`cdk-virtual-scroll-viewport` рисует видимые строки плюс буфер. У вьюпорта должна быть фиксированная высота. `itemSize` предполагает **одинаковую** высоту строки. Разная высота — экспериментальная стратегия или свой `VirtualScrollStrategy`. Часто лучше фиксированные строки, а детали — в боковой панели.

Подгрузка следующей страницы — по `scrolledIndexChange` ближе к концу. Подводные камни: липкие заголовки и таблицы требуют доп. работы; поиск браузера (`Ctrl+F`) не видит ненарисованные строки; скринридер видит только отрисованное, поэтому общее число строк надо объявлять отдельно.

Динамический тип компонента (виджет дашборда, плагин, модалка) создают через `ViewContainerRef.createComponent` после ленивого `import()`, либо декларативно через `ngComponentOutlet`. Inputs ставь через `setInput`, не прямой записью в поле: иначе OnPush и signal inputs не обновятся. Такой компонент уничтожается вместе с `ViewContainerRef` или через `ref.destroy()`.

## 13. SSR и гидратация

`@angular/ssr` рисует HTML на сервере. `provideClientHydration()` переиспользует этот DOM в браузере, а не создаёт его заново. Есть replay событий (клик до гидратации не теряется) и инкрементальная гидратация (`@defer (hydrate on viewport)`). Код только для браузера кладут в `afterNextRender` или за `isPlatformBrowser`.

Гидратация ждёт, что первый рендер клиента даст **ту же структуру DOM**. Расхождение — ошибки серии NG0500.

Причины: прямая правка DOM (`appendChild`, библиотека, которая сама лезет в узлы); невалидная вложенность, которую парсер браузера «чинит» (`<p><div>`, таблица без `<tbody>`); разные данные на сервере и клиенте (`Date.now()`, `Math.random()`, таймзона, `localStorage`); `window` / `document` / `localStorage` во время рендера. На сервере это ещё и падает.

`HttpClient` на время гидратации сам кэширует ответы, полученные на сервере. `ngSkipHydration` — последний выход для одного компонента, не стратегия.

Глобальный `ErrorHandler` ловит ошибки шаблонов, lifecycle, обработчиков и (с Zone) необработанный async. Ошибки `HttpClient`, которые ты уже поймал в `catchError`, он не видит: их репортят в interceptor. Покомпонентного error boundary как в React нет. Падение изолируют на уровне потока данных и рисуют error state виджета. Для ленивой загрузки есть блок `@error` у `@defer`.

## 14. Тесты

- Раннер: Jest или Vitest. Karma устарела.
- `TestBed` поднимает тестовый injector и создаёт компонент (`TestBed.createComponent`).
- Angular Testing Library — тесты с точки зрения пользователя.
- CDK Component Harnesses — взаимодействие с Material, CDK и своими компонентами дизайн-системы.
- `provideHttpClientTesting()` и `HttpTestingController` мокают HTTP.
- Время: `fakeAsync` / `tick` в приложении с Zone, либо фейковые таймеры раннера и `await fixture.whenStable()` в zoneless.
- Сквозные тесты: Playwright или Cypress.

OnPush-ловушка в тесте: присвоить `fixture.componentInstance.count = 5` и звать `detectChanges()`. Компонент не помечен грязным, view может не обновиться. Нужен `fixture.componentRef.setInput('count', 5)`. Ещё честнее — маленький хост, который биндит input так, как это делает приложение. `render` из Testing Library делает это сам.

`fakeAsync` крутит тест в фейковой зоне: время двигается только через `tick(ms)`. `flush()` прогоняет все таймеры, `flushMicrotasks()` — промисы. Если в конце остался интервал, тест падает. Нужен `zone.js/testing`. В zoneless берут `vi.useFakeTimers()` / `jest.useFakeTimers()`. Сложную RxJS-логику точнее всего проверять marble-тестами через `TestScheduler`.

## 15. Безопасность

Интерполяция всегда экранируется. Значения в `[innerHTML]`, `[style]`, `[href]` / `[src]` и resource URL санитизируются под свой контекст. HTML чистится от скриптов и обработчиков, стиль — от опасных значений, URL блокирует `javascript:`, ресурсный URL (`iframe`, `script`) запрещён, пока его явно не доверили.

`DomSanitizer.bypassSecurityTrust*()` выключает эту защиту. Это красный флаг на ревью, нужен повод. Прямая запись `nativeElement.innerHTML = ...` обходит Angular целиком. Недоверенный текст (строка лога, комментарий) рисуй интерполяцией или текстовыми кусками, не как HTML.

Поверх этого — CSP. Angular умеет nonce через `CSP_NONCE`. Где можно, Trusted Types. `HttpClient` сам поддерживает XSRF-токены для cookie-авторизации.

## 16. CLI и миграция большого приложения

`ng new`, `ng generate`, `ng serve` (dev-сервер на Vite), `ng build` (сборщик на esbuild) с бюджетами бандла. `ng update` тащит автоматические миграции. Схематики есть для standalone, control flow и signal inputs. Большие репозитории часто ставят сверху Nx.

План миграции длинного кода, который стоит рассказать по шагам:

1. Standalone схематиком, ленивые роуты становятся `loadComponent` / `loadChildren`.
2. Control flow: `*ngIf` / `*ngFor` → `@if` / `@for`.
3. Signal inputs, outputs, queries. Схематик просмотреть руками: input, который мутировали внутри компонента, сам не переедет.
4. OnPush по фичам. По пути чинить мутации и добавлять `track`.
5. Новое состояние на signals. На границе со старым RxJS — `toSignal` / `toObservable`. Рабочие потоки не переписывать «потому что модно».
6. Zoneless, когда OnPush и signals или `async` pipe уже покрывают приложение. Убрать опору на Zone, поправить тесты, включить `provideZonelessChangeDetection()`.

Между шагами: линт, который не пускает старый стиль в новый код, флаги, мониторинг ошибок и скорости. Фичи продолжают ехать, это не заморозка на переписывание.

## 17. Angular и React

Говори нейтрально. Войну фреймворков на собеседовании не любят.

| | Angular | React |
| --- | --- | --- |
| Что это | Фреймворк: роутер, формы, HTTP, DI, тесты, CLI | Библиотека UI плюс экосистема, которую выбираешь сам |
| Рендер | Скомпилированный шаблон пишет в DOM; change detection решает, что проверять | Компоненты описывают UI, reconciliation сверяет virtual DOM |
| Реактивность | Signals и RxJS; исторически Zone.js | State и повторный рендер |
| Переиспользование логики | Сервисы и DI, директивы | Хуки и context |
| Стили | Инкапсуляция по умолчанию | CSS modules, CSS-in-JS, Tailwind — на выбор |
| Сильная сторона | Одинаковые договорённости в большой команде, батарейки в комплекте, `ng update` | Гибкость, экосистема, проще для маленького приложения |
| Цена | Больше понятий: DI, RxJS, декораторы | Усталость от выбора и разнобой между командами |

Финальная фраза: обе стороны решают состояние, отрисовку и композицию. Для большого долгоживущего продукта с несколькими командами встроенные договорённости Angular — реальное преимущество. Архитектура, производительность и тесты переносятся между ними.
